# CONCEPTS

The theory this app is built on: what it is for, the rules that span modules, and the module map. Source of truth for scope is `docs/superpowers/specs/2026-10-14-files-rebuild-design.md`; later decisions are in `DECISIONS.md`. Where the code does not yet do what is written, the statement is the target and the gap is listed under *Known drift*. Recorded at the end of Phase B (2026-10-14).

## What the program is for

Files is a multi-cloud hub for the people of one shard: the owner (shard admin) and members, such as a family or a small team. It gives one interface over the shard's own storage and, later, the cloud accounts each member connects. Moving data from big-tech clouds onto the shard is a first-class flow.

- **Live, not mirrored.** Cloud files are shown live from the provider. Nothing is copied onto the shard unless the user explicitly copies or migrates it. There is no background two-way sync, so there are no sync conflicts.
- **Ownership.** Each member connects their own cloud accounts and only that member sees them. Sharing works the same for local and cloud files.
- **v1 scope** (spec §2.1): shard storage, Google Drive, Dropbox, OneDrive/SharePoint; browse, resumable transfer, migration, trash, versions, preview, search, sharing, WebDAV, PWA, three UI languages, the "Daylight Instrument" look.
- **Deferred, not rejected** (spec §2.2): tracked in one issue labelled `deferred`.
- **Built so far (Phase B):** OIDC login, deny-by-default, `resolveInRoot`, `LocalBackend`, the sources API, a Vue folder view with upload and download, E2E, container. Everything else in the spec is still ahead.
- **Fail fast.** Missing or invalid config stops the process at start-up (`exit(1)`); there are no fallback defaults.

## Identity model

- The only way in is the shard's OIDC provider: authorization code with PKCE. `state`, `nonce` and the verifier live server-side in a `login_attempts` row (cookie `__Host-fs_login`) and are single-use. A missing or mismatched value is rejected.
- Each person gets a stable internal user id (UUID), mapped from (`iss`, `sub`). Nothing is keyed by `sub`, display name or `X-Ptl-Client-Id` (a device id, not a person).
- The display name is taken at every login from `name`, then `preferred_username`, then the email's local part (`server/src/users.ts`). With none of them it is stored empty and the web shows the localized "Mitglied" (`web/src/memberName.ts`, used wherever a member is shown). It is never the id or `sub` (#337).
- The login name is taken at every login too: `preferred_username`, else the email (`users.login`, #321). Only `/api/v1/me` carries it, as `login`, for the phone setup page's user name; no member list shows it.
- The `admin` role comes from a configurable claim: `FILES_OIDC_ROLE_CLAIM` equal to / containing `FILES_OIDC_ADMIN_VALUE`. Everyone else is `member`. The pair is optional (both or neither); without it nobody is admin, because shard_core sends no role claim yet (freeshard#251).
- Sessions are rows in SQLite (only a hash of the id is stored), 14 days, revocable; the cookie is `__Host-fs_sid` on https and `fs_sid` on http loopback.
- Mutating requests need `Origin` equal to the public URL and an `X-CSRF-Token` matching the session. The token comes from `GET /api/v1/me`.
- There are no local accounts and no bypass. Dev, tests and E2E use the fake IdP in `server/test/support/fakeIdp.ts`. An `http://` issuer is accepted only for loopback.

## Sources and addressing

A file is identified by `{source, path}`: `home` (the member's own shard storage), `share:<id>` (something another member shared with the caller, #146) or `conn:<id>` (one of the caller's own cloud connections, #148). Every source route gets its backend and the caller's access (`read` or `edit`) from `resolveSource(req, source)` (`server/src/storage/resolveSource.ts`) before reading any input; no route builds a backend itself, and mutating routes answer `FORBIDDEN` without `edit`. An unknown or malformed source id is `SOURCE_NOT_FOUND` (404), never a fallback to `home` (#95). The API is one route family under `/api/v1/sources/:source/`: `list`, `stat`, `content` (GET with Range, PUT streaming upload), `mkdir`, `move` (also rename), `copy`, `delete` (to the trash), `zip` (a folder or a selection in one folder as a streamed ZIP), `thumbnail`; plus `/api/v1/trash` (list, `restore`, `delete`, `empty`; the home's local trash), `/api/v1/uploads` (resumable uploads over tus 1.0 and the caller's unfinished ones, see below), `/api/v1/recent` (the caller's recent items), `/api/v1/favourites` (the caller's favourites: list, star, remove), `/api/v1/tags` (the caller's tags: list, an item's, a folder's children's, `items` of one tag, `add`, `remove`), `/api/v1/smart-folders` (the caller's smart folders: list, create, replace, delete, `results`), `/api/v1/comments` (an item's thread, a folder's children's counts, post, edit, delete), `/api/v1/search` (name search), `/api/v1/shares` (create, who has access, `incoming`, revoke), `/api/v1/members` (the other members, for the share picker), `/api/v1/links` (public links: create, list per item, change, revoke), `/api/v1/connections` (the caller's cloud connections: list with the offered providers, `authorize`, the provider's `callback`, `check`, unlink, and for SharePoint `sites`, a site's `libraries` and picking the `library`), `/api/v1/transfers` (copies and moves between sources as jobs: create, list, one job, its CSV `report`, `cancel`, `dismiss`, `clear`, and the SSE `events`), `/api/v1/renames` (batch rename in one folder: `preview` and create, a transfer job of kind `rename`), `/api/v1/duplicates` (the caller's duplicate scan: state, `scan`, `cancel`, `trash`), `/api/v1/migrations` (a cloud folder or account onto the shard: `scan`, create, and the confirmed `cleanup`), `/api/v1/versions` (a file's versions or provider revisions: list, `content`, `restore`), `/api/v1/storage` (the caller's storage overview), `/api/v1/admin/members` (the admin's member list with usage and quota, and `:id/quota`; everyone else gets `FORBIDDEN`), `/api/v1/admin/disk` (the data volume and its reserve, admin only), `/api/v1/app-passwords` (the caller's app passwords for WebDAV: list, create, revoke), `/api/v1/requests` (file requests: create, list, change, revoke, a request's received `files`, `seen` and discarding its unfinished `uploads`), `/api/v1/me`, `/auth/*` and `/healthz`; visitors of a public link use `/s/<token>/…` (`info`, `unlock`, `list`, `content`), visitors of a file request `/r/<token>/…` (`info`, `unlock`, and tus `uploads`). A `list` answer carries the caller's `access` to the source. Errors are `{ code, params }`; codes and HTTP statuses live in `shared/` and the client translates them.

All data-root locations (`files.db`, `homes/<userId>`, `thumbs/`) are derived in `server/src/paths.ts`.

Content is served inline only for an allowlist (images except SVG, video, audio, PDF, `text/plain`) with `Content-Security-Policy: sandbox`; everything else is an attachment. The MIME type comes from the extension only (`storage/mime.ts`), never from the bytes.

The preview overlay (#142) loads files through that same content route. Images, video and audio point their element at it. PDFs are drawn by pdf.js on a canvas, because the browser's own viewer refuses a sandboxed document. Text and Markdown are fetched with a Range request capped at 512 KiB. Markdown is parsed by markdown-it with raw HTML off, and `web/src/markdown.ts` builds Vue nodes from an allowlist of elements, so no HTML string ever reaches the DOM and no image is loaded. The SPA picks the viewer from the listed `mime` (`web/src/preview.ts`), and the server's allowlist stays the guard.

Thumbnails (#144) come from `thumbnail` (`size` 128, 256 or 512): a WebP whose longer side has that many pixels. Local ones are generated on first request (`storage/thumbnails.ts`): images by `sharp` in the process, a video frame by ffmpeg, a PDF's first page by `pdftoppm`. Tools get only the absolute path from `resolveInRoot` in an argument array without a shell (after `--`, or as `file:` with a fixed demuxer and only the file protocol), with a time limit and at most two generators at once. They are cached under `<DATA_DIR>/thumbs/` (`paths.ts`), outside every home, with one `thumbnails` row each; a row whose source ETag changed is regenerated, the least recently used ones go once the cache exceeds its cap, and every write, move or delete through the app drops the thumbnails of the paths it touched. Cloud backends will proxy the provider's thumbnail through `StorageBackend.thumbnail?`. The folder view shows them in the list and in the gallery view, whose tiles open the preview overlay as the lightbox.

A ZIP download is built while it is sent. It walks only the backend's own `list` and `read`, so it holds exactly what a listing shows: no symlinks, no `.files/`, no temp files. Entries are stored, every file is ZIP64 with a data descriptor, and names are relative and UTF-8. Nothing is buffered or written to disk except the central directory. An error after the first byte aborts the response instead of ending a short archive.

## Storage interface

All file access goes through `StorageBackend` (`server/src/storage/backend.ts`): `list`, `stat`, `read` (with range; returns the `Entry`, the stream and the ETag in one call, resolving the range against the opened file's size), `write` (streaming, with a collision policy, a byte limit, an optional declared `size` and an optional `ifMatch` ETag), `mkdir`, `move`, `copy` (both with a collision policy) and `delete` (a batch, to the trash). `LocalBackend` implements it on `<DATA_DIR>/homes/<userId>`, together with a `HomeIndex` (the database, the user id and the path-dependent tables). Every path passes `resolveInRoot(root, userPath)`:

- it rejects NUL and control characters, bidi controls, ill-formed UTF-16, `..` segments, absolute paths and over-long paths;
- it `lstat`s every existing component and rejects symlinks;
- it `realpath`s the deepest existing ancestor and checks it lies under the root with a trailing separator.

Writes stream into a hidden temp file `.<16hex>.upload` in the target directory, are `fsync`ed and then renamed (or hard-linked for "keep both"/"fail if exists"). The target directory is `fsync`ed after that, so the new entry survives a crash. "Fail if exists" answers `FILE_EXISTS` with the taken `name` in `params` before the body is read, so the SPA can ask the collision question without uploading twice. "Keep both" names are `name (n).ext`, starting at `(1)`, within 255 bytes, cut at whole characters; the extension is dropped only when not even one character of the name fits before it. Temp files left behind by a crash are removed by a sweep over every home in an `onReady` hook, so it finishes before the server listens; it removes only regular files with exactly that name and never follows symlinks. `<root>/.files/` is reserved for trash, copy staging (`tmp/`), resumable uploads (`uploads/`) and versions (`versions/`) and cannot be addressed by users; the backend reaches it only through `resolveInRoot`.

Resumable uploads (tus 1.0: creation, `HEAD`, `PATCH`, termination, expiration) collect their bytes in `<home>/.files/uploads/<id>`; an `uploads` row holds the target, the declared length, the collision policy, the expiry and `received`, the bytes fsynced so far. Everything that can be refused is refused at creation, before a byte exists: the size limit, the quota, the path, a folder in the way and, under `fail`, a taken name. A `PATCH` continues exactly at `received`, never stores more than declared (a client that sends more loses the whole upload), and records what arrived even when the connection drops. Once all bytes are in, they are renamed into place with the policy in the transaction that deletes the row, creating missing parent folders (folder upload); a name taken meanwhile answers `FILE_EXISTS` and keeps the bytes for `finish`. Ids are looked up with the member, so another member's upload is 404. Uploads idle for 24 hours are removed by an hourly job. `GET /api/v1/uploads` (not tus) lists the member's own open uploads into their home, never a visitor's upload through one of their file requests (#233): after a reload the upload panel offers each one with "Resume" (pick the file again; the client continues at the server's offset only if this browser sent that upload from that very file, by target, size and modification time, else it discards the old upload and sends the file anew) and "Discard" (termination, which frees its reserved quota). While uploads run, leaving the page asks first (`beforeunload`); a batch that finished without a failure leaves the panel after five seconds.

A member may have a quota (`users.quota_bytes`; none by default), which only the admin sets on the members page (#156). Usage is everything under the home (files, trash, versions, staged uploads and interrupted copies), plus what the member's open uploads still have to send. Everything that adds bytes to a home is checked before it is accepted: uploads (tus creation and `PUT content`, again while they stream), copies within the home (the source's size), trash restores (the item's size, because a restore keeps bytes the trash would free) and transfer and migration items (through the home's `write`, with the announced size). Writes and copies reserve their size before a byte is read (all the free space without a declared length), in memory under the member's lock that tus creation, restore and purge also take, so writes running together never share the same free bytes (#197). A version restore swaps bytes already counted and is not checked. Beside every member's quota stands the shard's **disk reserve** (#320, `storage/diskReserve.ts`): Files refuses with `STORAGE_FULL` (507) any write that would leave less than `max(5 GiB, 5 %)` of its data volume free, or what `FILES_DISK_RESERVE` says (`10GiB`, `8%`; validated at start), so a member never fills the disk the platform and every app share (freeshard#261). The free bytes come from `statfs` of `FILES_DATA_DIR` (`bavail`), minus the rest of every member's open tus uploads and of every write or copy in flight, under one lock across members; it is checked at the same points as the quota, after it: tus creation (and each `PATCH`, since the disk may have filled meanwhile), `PUT content` and WebDAV PUT (a declared size is held before a byte is read; without one, the write may fill what was left at its start and asks again every 16 MiB), copies, trash restores and transfer and migration items into the home. File request uploads are tus uploads of the owner's home, new versions are writes with "replace". Thumbnails are not made below the reserve plus 1 MiB (`NO_THUMBNAIL`, cached ones are still served). Deleting, emptying the trash and revoking links never ask. The admin sees the volume and the reserve on the storage page, and from 90 % used (or once only the reserve is free) a banner under the header. `GET /api/v1/storage` shows the caller's usage by kind against the quota, each connection's provider quota (`StorageBackend.quota?`; a failing provider as its error code) and the home's ten largest folders, summed from the name index.

Moves, deletes and "replace" run in one SQLite `BEGIN IMMEDIATE` transaction around synchronous renames, which are undone in reverse if anything after them fails, so files and rows never disagree (spec §3.6). "Replace" sends the old item to the trash, never deletes it. Delete renames the item to `.files/trash/<id>` and writes a `trash` row; a batch is all or nothing. A folder never moves or copies into itself or a descendant (`TARGET_INSIDE_SOURCE`). Copies are built in `.files/tmp/` with `copyFile` (kernel copy, no buffer) and renamed into place; the startup sweep empties `.files/tmp/`. Rows that point at home paths (`recent`, `name_index`, `shares`, `public_links`, `versions`, `favourites`, `dav_props`, `file_requests`, `tags`, `comments` and `content_hashes`) are listed in `PATH_TABLES` (`server/src/storage/pathRefs.ts`): a move rewrites the item's rows and those beneath it, a delete removes them (or, for a table with an `orphanColumn` such as `shares`, marks them orphaned, or, for one with a `trashColumn` such as `versions` and `tags`, hands them to the trash item), in the same transaction. Rows still pointing at a move's or a restore's free target are stale (changed outside the app) and give way first, except those of a table with `bytes` (`versions`), which stand for bytes on disk.

Versions (#154): replacing a file's content in the home (`PUT content` or tus with "replace", also through a share with `edit`, and restoring a version) renames the old bytes to `<home>/.files/versions/<id>` with a `versions` row, in the transaction that puts the new bytes in place. Per file the newest are kept within `FILES_VERSIONS_MAX_COUNT` and `FILES_VERSIONS_MAX_BYTES`; the older ones go, bytes first. They count towards the quota, follow moves, go to the trash with their file (`trash_id`), come back with its restore and are purged with it (`TRASH_TABLES`). Restoring a version renames its bytes onto the file and keeps the replaced content as a version. Cloud backends list the provider's revisions (`revisions?`, the newest `current`) and restore them where the API allows (`restoreRevision?`: Dropbox, Graph; not Drive). The details drawer shows them (`VersionHistory`).

Recent: every write in the home (upload by `PUT` or tus, copy, move, rename, restore) records the item it placed in a `recent` row of its member, inside the write's transaction (`server/src/storage/recent.ts`). Writing a path again moves it to the top; each member keeps the newest 100. `GET /api/v1/recent` lists only the caller's own rows, newest first; there is no feed of other members' actions.

Favourites (#155): a `favourites` row pins one item of any source the member can read (`{member, source, path, type}`); starring resolves the source and `stat`s the item first. Home rows are in `PATH_TABLES`: they follow moves and go with deletes in the operation's transaction. In another source the sources route rewrites or removes the caller's rows of that source after the provider's move or delete succeeded. Unlinking a connection marks its rows gone (`gone_at`, the table's `goneColumn`), and the list also resolves each remaining source through `sourceFor`, so a favourite of an unlinked connection or a revoked share is listed as `available: false`, never resolved against another source. `GET /api/v1/favourites` lists the caller's own rows in the order they were starred.

Tags (#212): a `tags` row is one tag of a member on one item of any source they can edit (`{member, source, path, type, name, name_fold}`); a tag is the set of a member's rows with one `name_fold` (NFC, lower case) and has no row of its own, and the member's first spelling names it everywhere. Names are trimmed, 1 to 40 characters, without control or bidi characters (`normalizeTagName` in `shared/`), at most 20 per item (`TAG_LIMIT`); a multi-select "Add tag" is one all-or-nothing transaction. Adding resolves the source with `edit` and `stat`s every item first; removing touches only the caller's rows, so a tag of a missing item or a gone source can always go. Home rows are in `PATH_TABLES` and follow moves; a delete to the trash hands them to the trash item (`trash_id`, `TRASH_TABLES`), so they come back with a restore and go with the purge. In other sources the sources route rewrites or removes the caller's rows after the provider's move or delete (as for favourites), and unlinking a connection marks its rows gone. The tag view (`GET /api/v1/tags/items?name=`) `stat`s every item in its own source on open, per source within `FILES_SOURCE_TIMEOUT_MS` and at most `STAT_CONCURRENCY` (6) at once (`mapLimit`, #307), the first `MAX_RESOLVED` (500) items in tag order with `more` for the rest: an item is `ok`, `missing` (changed outside Files), `unavailable` (its source is gone) or `failed` (its source did not answer). The colour of a tag is one of five design tokens, hashed from its folded name (`tagColor`).

Comments (#213): a `comments` row is one comment on one item, keyed by where the item lives for its owner (`{owner, source, path}` with the owner's `home` or `conn:<id>` and path; `keysOf` maps a grantee's `share:<id>` path beneath the share's root onto it), so the owner and every grantee read one thread; it holds the author, the text and created/edited. Every request names the item as the caller reaches it: the source is resolved and the item `stat`ed first, so no access, a revoked share and an unknown item are all 404 before a comment is read. Anyone who reaches the item may comment (`read` too), up to 500 live comments per item and 20 000 per author, trashed ones included (`COMMENT_LIMIT`, counted with the insert under one write lock, #308); the author edits, the author or the item's owner deletes. The text is plain (`normalizeCommentText` in `shared/`: NFC, LF line ends, trimmed, 1 to 4000 characters, no control characters but line feed and tab, no bidi controls) and always rendered as text. Home rows are in `PATH_TABLES` with the item's owner as the owner and follow moves (also a grantee's inside a share), go to the trash with the item and come back with its restore (`TRASH_TABLES`); cloud rows follow moves through the sources route (also through a share) and are deleted with a delete through the app, a transfer's or cleanup's delete of the original, and an unlink of the connection. `GET /api/v1/comments/folder` gives the counts of a folder's children for the list's badges.

Smart folders (#214): a `smart_folders` row is a member's saved `SmartQuery` (`shared/src/smartFolders.ts`: name contains, types, tag, changed within N days, size range, sources; structured values only, combined with AND, at least one criterion), evaluated on every open and never cached. `GET /api/v1/smart-folders/:id/results` asks every chosen source at once (default: the home and every connection, as global search; shares are not searched), each within `FILES_SOURCE_TIMEOUT_MS` (`withinTime`, `SOURCE_TIMEOUT`), and answers one group per source like global search, a failing one with its code (`sourceFailure`). The home answers from `name_index` (joined with `tags` for a tag) without touching the disk; a cloud answers its tagged items (the first 500, `stat`ed 6 at a time, #307) when the query has a tag, else the provider's `search` for the name post-filtered on type, size and date (`SEARCH_NEEDS_NAME` without a name, `NOT_SUPPORTED` without `search?`). Types are decided by extension, like every type in the app.

Search (#145): every file and folder in a home has a `name_index` row of its member (path, folded name, type, size, modified). The fold (`foldName`) drops accents (nonspacing marks) and case, so "umlaut" finds "Ümlaut" (#235); the query is folded the same way, and migration 026 refolded older rows through the SQL function `files_name_fold` that `openDb` registers from it. Clouds search as their provider does. Every write that places an item (upload by `PUT` or tus, `mkdir`, copy, move, rename, restore) writes its row, the rows of the folders created on the way and, for a copied or restored folder, the rows of its whole tree, inside the write's transaction; moves and deletes reach the rows through `PATH_TABLES`. The home answers `search` from the index without touching the disk, matching the query literally with `instr` (no `LIKE`, so `%` and `_` are plain characters). `GET /api/v1/search?q=` asks the home and every connection whose backend has `search?` at once, at most 50 results each (`more` when there are further ones), and answers one group per source; a source that fails is a group with its error code (`SEARCH_FAILED` for anything that is not an `AppError`), never a failed request. Changes made on disk outside the app reach the index only through the rebuild command (`server/src/reindex.ts`).

Sharing (#146): a `shares` row grants one member `read` or `edit` on one item of the owner's own source (`{owner, source, path, grantee, access}`); the owner is always the caller who creates it, and a share is never shared on. The grantee opens it as `share:<id>`: `resolveSource` reads the row with the grantee on every request (anyone else: `SOURCE_NOT_FOUND`) and wraps the owner's backend (the owner's home, or later the owner's connection, reached on the server) in a `ShareBackend` (`server/src/storage/shares.ts`), where `/` is the shared item and every path lies beneath it, normalised before it is prefixed. The item itself is never renamed, moved, copied or trashed through the share, and a write at `/` is `FORBIDDEN` unless it overwrites a shared file as itself ("replace" or "fail"). "Keep both" would place a new name beside the item, outside the share, and a cloud source would replace a shared folder with a file (#252). The share follows moves of the item through `PATH_TABLES`; a delete or replace orphans it, and it then answers `SHARE_ORPHANED` (410), never falling back to whatever takes the old name. "Shared with me" (`/api/v1/shares/incoming`) shows only the item's own name, never the owner's folders above it. Members are the people who have signed in to Files once. The SPA offers sharing in the home and the member's own connections, and upload into an `edit` share by one streaming `PUT` per file into the owner's source (#208). A share of a cloud item names a path: only home moves cascade, so a cloud item renamed elsewhere answers 404.

Public links (#147): a `public_links` row lets anyone with its token (16 random bytes, base64url) reach one item of the owner's own source at `/s/<token>`, proxied through the shard. The visitor's requests go to the one public route `/s/:token/*`, which checks on every request: an unknown or revoked token is `NOT_FOUND`, a deleted item or unlinked connection `SHARE_ORPHANED` (the row is in `PATH_TABLES` like `shares`, and the owner's source is reached through the same `ownerSource`, never a fallback), a passed expiry `LINK_EXPIRED`, and without the password `PASSWORD_REQUIRED`. The password is an argon2id hash; wrong attempts are limited per link and per address (429; each attempt is reserved in the same step as the check and counts while argon2 runs, so a parallel burst gets no more checks than the limit, #196), and a correct one sets a signed cookie scoped to `/s/<token>/` that names the link and the current password. Every byte-serving answer of `content` counts against `max_downloads` (NULL = no limit, 0 = none), previews and Range requests included, in one conditional `UPDATE`. The content is served through `ShareBackend` (confined beneath the item), always with `CSP: sandbox` and `nosniff`, inline only on request and only for the allowlist. An expiry the server cannot parse is refused when the link is created or changed, never taken as "no expiry". The page `/s/<token>` is the SPA (`PublicLinkView`) under the app's CSP, outside the signed-in shell, in the visitor's language; it gets everything as JSON and renders it as text. After a download or preview it asks `info` again until the count changed (#232), and mentions the limit only for a link that has one; the owner revokes a link only after a confirmation. The visitor sees only the link's own error codes and those of their request; whatever the owner's source reports about itself (a revoked grant, a rate-limiting provider, Drive's naming) is one `LINK_UNAVAILABLE` (503), with the real code logged with the link's id (#279). Local ETags are an HMAC of inode, size and mtime under a key derived from the session secret, so a grantee or visitor does not learn the inode (#279). The provider's own tags of a cloud item pass through unchanged.

File requests (#217): a `file_requests` row lets anyone with its token (16 random bytes) upload into one folder of the owner's home or own cloud connection at `/r/<token>`, without seeing it. The public route `/r/:token/*` only accepts: `info` (the title, the limits left and the visitor's own uploads of this session under the names they sent, never the folder, its name or contents; not even the saved keep-both name, whose ` (1)` would reveal that the folder holds the name, #305), `unlock`, and tus creation, `HEAD` and `PATCH` under `uploads`; there is nothing to list or download. Each request is checked like a public link's (unknown `NOT_FOUND`; revoked `LINK_REVOKED`, deleted folder or unlinked connection `SHARE_ORPHANED`, passed expiry `LINK_EXPIRED`, all 410; the same password limits, with one per-address limiter shared with public links), mutating requests need the app's `Origin`, and the visitor is a random id in a signed cookie scoped to `/r/<token>/` that also carries the unlock. Every visitor upload is a tus upload of the **owner's** home (`LocalBackend.createUpload`), so the owner's quota and the size limit are checked at creation and the declared length is enforced while streaming; a cloud target also needs the provider's free space, and its bytes are staged in the owner's home and written into the cloud folder once complete (`UploadPlacement`). The name is sanitised (`sanitizeUploadName`: the last segment after `/` or `\`, no control characters, no leading dots or trailing dots and spaces, at most 255 bytes) and placed with keep-both in the folder as it is at the end (it follows moves, `PATH_TABLES`). A `file_request_uploads` row per file is reserved in one write transaction against `max_files` and `max_bytes` before the tus upload opens, so parallel creations never pass a limit; a row counts while reserved, open or received, and stops counting once its upload expired or was dropped. Open uploads hold the owner's quota, so they are bounded and released (#304): at most 10 per visitor and 100 per request (`REQUEST_UPLOADS_OPEN`, checked in the same transaction); revoking a request terminates them, the owner can discard them while keeping the request open (`pending` in the list), and the hourly upload expiry job terminates those of any revoked, orphaned or expired request. Received rows carry the saved name, the optional uploader name (kept only if the request asks for it) and `seen_at`, which clears the owner's badge ("N new").

Cloud connections (#148): a `connections` row holds one provider account of one member, with the refresh token sealed by AES-256-GCM (`cloud/secretBox.ts`, bound to the row's id) and a status (`ok`, `reauth`; `unavailable` when the shard no longer offers the provider, `library` while a SharePoint connection has no library yet). Providers are definitions with fixed endpoints passed to `buildApp`; production offers each one whose client credentials are configured (`configuredProviders`: Google Drive with `FILES_GOOGLE_CLIENT_*`, #149; Dropbox with `FILES_DROPBOX_CLIENT_*`, #150; OneDrive and SharePoint with `FILES_GRAPH_CLIENT_*`, #151; pCloud with `FILES_PCLOUD_CLIENT_*`, #211), tests and the E2E cloud server bring the fake provider (`server/test/support/fakeProvider.ts`). Connecting is the authorization code flow: `state` and the PKCE verifier live only in a `connect_attempts` row bound to the session, single-use, 10 minutes; the redirect URI comes from the configured public URL; a callback without a matching state stores nothing; nothing of the callback's query is logged. `OAuthClient` (`cloud/oauth.ts`, one per connection and process) keeps the access token in memory, refreshes it before expiry or after a 401 in a single flight, writes a rotated refresh token before using the new access token, marks the connection `reauth` when the provider refuses the grant (`CONNECTION_REAUTH`), and retries 429/5xx with `Retry-After` or exponential backoff plus jitter (`PROVIDER_UNAVAILABLE` after that). `conn:<id>` resolves only among the caller's own connections. Unlinking removes the row, orphans every share and public link into it and marks the member's favourites in it gone, in one transaction (`orphanSourceRefs`); they never revive when the account is connected again.

Google Drive (#149): `GoogleDriveBackend` (`cloud/googleDrive.ts`) shows "My Drive" live over Drive v3 through the connection's `OAuthClient`; shared drives are out. Paths are resolved to ids one segment at a time and cached for 30 s per connection (changes through the app drop their paths at once). Drive allows one name twice in a folder and names a path cannot hold; such items are listed as `name (~<fileId>).ext`, which resolves to exactly that item, and the bare name of a duplicate is `AMBIGUOUS_NAME`, never the first match. Google Docs, Sheets and Slides are listed as `.docx`/`.xlsx`/`.pptx` and exported on download (unsized: no `Content-Length`, no ranges); other native types are `NOT_EXPORTABLE`. Downloads pass the Range on and follow a redirect only to Google's content hosts, without the bearer token; uploads go through a resumable session in 8 MiB chunks and resend from the Range of each 308, since Drive may keep less than a chunk (at most two chunks in memory); an empty file is one multipart request (#204); delete sets `trashed: true`, never a permanent delete; thumbnails are Drive's, fetched by the server and re-encoded as WebP, so no Google URL reaches the client. They come in two link shapes: `lh3.googleusercontent.com/…=s220` for stored files and `docs.google.com/feeds/vt?…&sz=s220` for Google Docs. The link gets the bearer token, because Drive requires it for private files, but only on Google's thumbnail hosts; a redirect from it is followed like a download, without the token (#203). The SPA uploads into a connection with one streaming `PUT content` per file (`web/src/api/directUpload.ts`), since tus places only into the home.

Dropbox (#150): `DropboxBackend` (`cloud/dropbox.ts`) shows the account's whole Dropbox live over the API v2 through the connection's `OAuthClient`. Dropbox addresses items by path and its paths ignore case, so every path comparison is made lowercased: a name taken in another case is taken, a rename that only changes case goes through a temporary name, and copying an item onto itself in another case never deletes it. `list` hands one `list_folder` page per call to the client; `next` is Dropbox's cursor bound to the folder it lists (`list_folder/continue`), so it cannot continue another folder. Downloads pass the Range on; uploads go through an upload session in 8 MiB chunks, one chunk in memory, committed with `add`, `overwrite` (replace, a new revision) or `update` with the revision (`If-Match`); delete is `delete_v2` into Dropbox's deleted files, never a permanent delete; thumbnails are Dropbox's, re-encoded as WebP. A Dropbox folder has no modified time, so `Entry.modified` is optional and the UI shows none.

Microsoft Graph (#151): `GraphBackend` (`cloud/graph.ts`) is one backend for OneDrive and SharePoint, offered as two providers over one Azure app. A OneDrive connection shows the account's own drive (`/me/drive`) after one consent. A SharePoint connection shows one document library (`/drives/{id}`): after the consent the member picks a site and one of its libraries in `LibraryPicker`; until then its status is `library` and `conn:<id>` is `SOURCE_NOT_FOUND`, and once picked the library never changes (another library is another connection; the row's `drive` and `drive_label`). Every API request goes to the Graph API; listings follow `@odata.nextLink` to the end, only below that API. Downloads, thumbnails, upload sessions and copy monitors are pre-signed URLs, called only on Microsoft's content hosts and without the bearer token: a download follows the 302 of `/content` on the server with the Range passed on; uploads go through `createUploadSession` in 10 MiB chunks, one chunk in memory, with conflict behaviour `fail` or `replace` (a new version; If-Match is checked by Graph); a copy is Graph's asynchronous copy, polled through its monitor until it is done. Names ignore case like Dropbox's. Delete puts items into the drive's recycle bin, never a permanent delete; search walks each result's parents for its path; thumbnails are Graph's, re-encoded as WebP.

pCloud (#211): `PcloudBackend` (`cloud/pcloud.ts`) shows the account's whole pCloud live over pCloud's HTTP JSON API. The consent's redirect names the API host of the account's region (`hostname`). Only `api.pcloud.com` (US) and `eapi.pcloud.com` (EU) are accepted, and the code is traded there. pCloud's token never expires and comes without a refresh token, so the provider is `longLived`: the connection seals the token with its host in place of a refresh token, the `OAuthClient` never refreshes it, and the host is checked against the allowlist again on every request. pCloud answers failures, a refused token included, with HTTP 200 and a `result` code. The backend maps those codes; a refused token marks the connection `reauth` (`client.refused()`). Folders list whole (no cursor). A download asks `getfilelink` and streams from the first content host on the allowlist (`*.pcloud.com`, https), without the token and with the Range passed on. Uploads go up in 8 MiB `upload_write` chunks, one chunk in memory, and end with `upload_save`, which gives an existing file a new revision; an upload that is not saved is deleted. Moves and copies happen at pCloud; a folder copy creates the target and copies the contents into it. Deletes go to pCloud's trash. Thumbnails are pCloud's `getthumb`, re-encoded as WebP, and only asked for files whose metadata says `thumb`. Revisions are `listrevisions` and `revertrevision`. pCloud's documented API has no search, so a pCloud connection is not searched.

Transfers (#152): a copy or move between two sources is a job (`storage/transfers.ts`): a `transfer_jobs` row and one `transfer_items` row per file or folder, a folder's children added when it is listed. Both sources are resolved with the owner's rights when the job is created and again for every item (`sourceFor`). Workers run in the process, at most two items at a time; a file streams from `read` into `write` through a meter that counts and hashes it, and is done only once verified: the bytes read match the announced size, the target's `stat` shows exactly that size, and where a side offers `digest` (SHA-256; only the home today) it equals the hash of what was sent. A job is `completed` only if every item is done, else `completed_with_errors` with the failed items. A move deletes nothing while it runs; at its end the source of each done item goes to the source's trash, whole folders where everything beneath is done, so a failed item keeps its source. Cancel stops new items and aborts those in flight, whose writes remove what they staged. At start-up, items in flight become pending again and running jobs continue; done items are never redone. Progress goes to the owner only, over SSE (`GET /api/v1/transfers/events`). The SPA asks the collision question for taken names before it starts a job, and shows the jobs in the transfer panel. Name rules (#342, `shared/src/nameRules.ts`): each backend declares its set (`onedrive`, `sharepoint`, `dropbox`, else `universal`) and refuses a breaking name with `NAME_NOT_ALLOWED` before it calls the provider; the listing carries the set, so the SPA asks about such a name first (`NameRulesDialog`, the suggestion with `_` for each forbidden character) and sends the chosen `name` with the item, while names a job meets on its own land under the suggestion and are listed in its `renamed` and the report. A job names what the member picked (`picked`, and the first 20 `names`, #234); `POST /api/v1/transfers/:id/dismiss` removes one ended job, which the panel does by itself 5 s after it showed a completed or cancelled one (not a migration) on a visible page.

Batch rename (#215): `planRenames` (`shared/src/batchRename.ts`) is a pure function from the selected names (in the list's order), the folder's names and the operations (find and replace as plain text, capitals, a numbering pattern with `{n}`, `{n:03}` and `{name}`, prefix and suffix; on the name without its extension unless asked) to one row per item: the new name, the action (`rename`, `unchanged`, `skip`) and a conflict, `invalid` (empty, `/`, over 255 bytes, reserved), `batch` (another item of the batch gets the name, or a selected item holds it) or `exists` (an item outside the batch holds it), compared in NFC ignoring case. A conflict is resolved only by a policy it allows (`ALLOWED_POLICIES`: an invalid name is skipped, a selected item is never replaced); "keep both" picks the free `name (n)` in the plan. `POST /api/v1/renames/preview` lists the folder and answers the plan; `POST /api/v1/renames` lists it again, computes the same plan and refuses with `RENAME_CONFLICT` while a conflict is open, else starts a transfer job of kind `rename` (same source on both sides) with one item per changed name. Each item is one `move` of the source (atomic in the home), followed by `followMove` for favourites, tags and comments; a failed item fails alone and the job lists it, like any transfer.

Duplicate finder (#216): `DuplicateFinder` (`storage/duplicates.ts`) runs one scan per member in the process over the home and the member's own connections (never a share). It lists every file (at most 200,000), keeps those whose size another file shares (empty files excepted) and groups them by size and hash within one algorithm: the home's SHA-256, read at most at `FILES_DUPLICATE_SCAN_BYTES_PER_SECOND` and cached in `content_hashes` with size and mtime (in `PATH_TABLES`), or a cloud's own hash from its listing (Drive's MD5, Dropbox's content hash, Graph's SHA-1 or quickXorHash), which a backend attaches beside the entry with `withHash` and never puts into the JSON; a file without one is counted as `unhashed`. Cancel aborts the listing or read in flight and keeps nothing. The result lives until the next scan or a restart. `POST /api/v1/duplicates/trash` takes copies of the last completed scan's groups: never every copy of a group (`DUPLICATE_LAST_COPY`), a kept copy must still match, and every picked copy is checked again right before its delete (the home's bytes hashed again, a cloud's hash from a fresh `stat`; `DUPLICATE_CHANGED` otherwise); it goes to the source's trash, followed by `followDelete`.

Migration (#153): a job of kind `migration` copies one folder of the member's own connection (`/` is the whole account) into a new folder of the home, created with "keep both" so it never mixes with or replaces anything the member has; it is a #152 job in every other way (resume, progress, verification). Every job works on its folders (and picked items not yet looked at) before its files; a folder's children get their type from its listing. A job answers `files` (file items known so far) and `listing` (folders still unlisted), so a migration's page says "Counting …" until the tree is listed and then "n of m files" with the same file count as the scan (#227). Where the provider's `read` gives its own hash of the file (`hash`; Google Drive's MD5), the received bytes are hashed with it too; each item records the checks it passed (`size sha256 md5`). `GET /api/v1/migrations/scan` counts files, folders and bytes for the wizard's review (it stops after 50,000 entries or 15 s and then says so). `GET /api/v1/transfers/:id/report` exports any job as CSV, one row per item, streamed page by page. The cleanup deletes the originals of verified files only: `GET /api/v1/migrations/:id/cleanup` (once the migration has ended) answers what would go and a single-use confirmation token (hashed in the row, 10 minutes), and only `POST` with that token starts a job of kind `cleanup` (its `origin` the migration) whose items are exactly the migration's done files. Right before each delete, the shard copy must still have the verified size and SHA-256 (`COPY_CHANGED`) and the original its size and modified time (`SOURCE_CHANGED`); the original goes to the provider's trash. Folders are never deleted.

Archive import (#322): `POST /api/v1/imports` starts a job of kind `import` from ZIPs already in the member's home (the import page uploads them by tus into the target folder first) into a home folder, one item per archive. An archive item opens the ZIP through the home's ranged `read` (`storage/archive.ts`, yauzl; only the central directory is read, nothing is copied), refuses it as a whole before anything is written (absolute paths, `..`, backslash or NUL, symlink or device entries: `ARCHIVE_UNSAFE`; encrypted or not stored/deflate, or not a ZIP: `ARCHIVE_INVALID`; over 200,000 entries, or expanding to more than 100 times its size and over 1 GiB: `ARCHIVE_TOO_LARGE`) and adds one item per entry. The layout decides the tree: Google Takeout keeps `Takeout/Drive/…` only, Apple's export `iCloud Drive/…`, a plain ZIP is taken as it is; `Google Photos` and `iCloud Photos` (photos belong in Immich) and other Takeout products become items with status `skipped` (reason `photos` or `other`), listed in the job's `skipped` and the CSV, never counted as failures. Every part of a split export lands in the same folder: folders merge with folders already there, a file whose name is taken follows the request's collision policy. An entry streams from the archive into the home's `write` (quota, disk reserve, declared size; yauzl checks the expanded size while it reads) with the entry's modified time. Resume, cancel and progress are those of every job.

WebDAV (#157): `/dav/` serves the member's own home over WebDAV class 1 and 2 (`server/src/dav/`), for Finder, Windows Explorer, davfs2 and rclone. It authenticates only with an app password over HTTP Basic (see *Deny by default*); the password's first 8 characters find its one row, whose argon2id hash is verified. Every operation goes through the home's `LocalBackend`: paths are decoded segment by segment from the request (never resolved by `new URL`) and pass `resolveInRoot`, PUT streams with "replace" (a version is kept) under the quota, DELETE and `Overwrite: T` go to the trash, MKCOL and PUT need an existing parent. ETags are size and modification time. Dead properties are `dav_props` rows in `PATH_TABLES`, outside the quota and bounded instead: at most 64 KiB each, 100 per item and 1 MiB per member counted with each row's path, with 507 beyond (#254); write locks (exclusive or shared, depth 0 or infinity) live in memory per member, at most 100 live ones each with at most 4 KiB of owner XML (#253), with the `If` header evaluated before the lock tokens are checked. GET answers as an attachment under `CSP: sandbox`. litmus (`pnpm test:litmus`) passes basic, copymove, props and locks. `server/test/davClients.test.ts` replays what the phone apps of the setup page send (#321: OPTIONS, PROPFIND depth 1 `allprop`, Depth: infinity refused with 403 `propfind-finite-depth`, LOCK/UNLOCK, MOVE with `Overwrite`, a chunked PUT with `Expect: 100-continue`), with an app password and without.

The trash is part of the home, so trashed bytes count towards the member's usage until purged. A trash row holds the original path, type, size (a folder's whole tree) and deletion time. Restore puts one item back at its original path through `resolveInRoot`, recreating missing parents, with the move's collision rules (never a silent overwrite). `LocalBackend.purge` is the only way out of the trash, for single delete, "empty trash" and expiry alike: bytes first, then the row and the rows in `TRASH_TABLES` in one transaction; if the bytes stay, the row stays, the error is logged and the caller sees the item as failed (`PURGE_FAILED`). The expiry job (`server/src/storage/trash.ts`) runs after start-up and hourly and purges what is older than `FILES_TRASH_RETENTION_DAYS` (default 30). Names that are not canonical on disk (NFD, control characters, invalid UTF-8) are skipped in listings. No code outside this layer builds filesystem paths, and no backend holds a whole file in memory.

## Deny by default

A global `onRequest` hook (`server/src/auth/guard.ts`) loads the session and then decides on the matched route. Every matched route needs a session, and a mutating one also the CSRF check, unless the route carries `config: { public: true }`. The allowlist is `/auth/login`, `/auth/callback`, `/healthz`, `/s/:token/*` (public links, guarded by token, password, expiry and limit in the handler), `/r/:token/*` (file requests, #217: guarded by token, password, expiry, revocation and the file and size limits; it never lists or serves the folder), `POST /api/v1/share-target` (the Web Share Target, #158: it never reads its body and only redirects, to login without a session), the SPA fallback and the static assets; the static plugin is registered in its own encapsulated scope whose `onRoute` hook marks exactly its routes public. Unmatched requests go to the not-found handler, which answers 401 without a session and 404 with one. The one other mode is `config: { appPassword: true }`, carried only by the WebDAV routes `/dav` and `/dav/*` (#157): the guard ignores the session cookie there and takes an app password over HTTP Basic (401 with a Basic challenge otherwise), and refuses a request whose `Origin` is not the app's; an app password opens no other route. Raw `req.url` is never used for a security decision, because the router decodes escapes (`/%61pi/`). `server/test/routeInventory.test.ts` walks the whole route table to enforce this.

A failed login (missing or expired attempt, state mismatch, IdP `error=`, failed code exchange) redirects to `/?loginError=1`; the reason is logged, never put in the URL. The SPA then shows `LOGIN_FAILED` with a link to sign in again instead of redirecting to login. Once `/api/v1/me` has answered, it replaces the URL without `loginError` (no reload), so a reload signs in normally instead of repeating the alert.

## Web addressing

SPA URLs are `/<source>/<folder path…>`; `/home/…` and `/share:<id>/…` are routed (the `:` stays unencoded) and `/` redirects to `/home`; `/s/<token>` is a public link's share page and `/r/<token>` a file request's upload page, both rendered without the shell or a session. `/share-target/<id>` is where a share from the phone (#158) waits for its folder. The source segment keeps folder names such as `api` or `auth` from colliding with server routes on reload, and leaves room for `conn:<id>` and `share:<id>`. The folder store holds the current `source` and builds every request from it (`web/src/api/paths.ts`).

## Known drift

- Google Drive (#149), Dropbox (#150), OneDrive and SharePoint (#151) and pCloud (#211) are the real providers. pCloud has no search and its files are not hashed for the duplicate finder; If-Match on a pCloud upload is checked just before the upload, not atomically. Drive shows only "My Drive" (no shared drives); none adds anything to Recent yet. A Dropbox or Graph delete that fails halfway leaves the items before it in the provider's deleted files or recycle bin (no transaction at the provider). A SharePoint connection's library cannot be changed (connect another one), and national Microsoft clouds are not supported. The share dialog is offered only in the home; a connection's folder view uploads (one `PUT` per file, not resumable across a reload) but has no share button yet.
- Members are whoever has signed in to Files once; there is no member directory from shard_core yet. Upload into a share is not offered in the SPA. Copies and moves between a share with `edit` and another source run as transfer jobs (#152); a read share offers no copy in the SPA yet.
- No platform language preference yet (freeshard#168): without a language setting (#159) the browser decides. The installed app's title bar colour (`theme-color`) follows the device, not an explicit theme setting.
- Tags and favourites name paths: a cloud item moved at the provider, or an item a share's owner moved inside the share, keeps the grantee's or member's old path and shows as missing in the tag view. Smart folders ask the same sources as global search (no shares), and a cloud only by a name or a tag.
- Search covers the home and every connection whose backend has `search?` (Google Drive, Dropbox and Graph have, #149–#151; their word matching finds a subset of a substring search). Shares are not searched (decided in #146). The index sees changes made outside the app only after the rebuild command.
- WebDAV serves the home only (no shares, no cloud sources), its locks are lost on restart, and PROPFIND refuses Depth: infinity. Public links to cloud files exist only through the API (the share dialog is home-only); a link to a folder offers no ZIP. Thumbnails exist for the home and every cloud provider. Drive revisions are listed but not restored, and cloud revisions cannot be downloaded (#154). Move and copy within a source are direct requests, not the persistent jobs of spec §3.4; only those between sources are jobs (#152). See spec §2.1 and the Phase D queue.
- Transfer verification compares SHA-256 where the home is one side, and Google Drive's MD5 of the source file (#153); Dropbox's `content_hash` and Graph's `quickXorHash` are not checked yet (DECISIONS, #152, #153). A failed migration item is not retried by itself; the member migrates that folder again. A migration cleanup leaves the (possibly empty) folders in the cloud. A cancelled move that the app restarts before it has deleted its done sources keeps both copies.
- The PWA (#158) caches only the app shell, no file data. A share needs the service worker: one sent before Files was ever opened on the device lands on a page that asks to share again. Shares are saved into My storage only.
- Routes Zod-parse params, query and body, but there are no Zod response schemas and no generated OpenAPI document (spec §3.3).
- The web API client is handwritten (`web/src/api/client.ts`), not generated from `shared/` (spec §3.8).
- The fake provider (`server/test/support/fakeProvider.ts`) speaks a generic protocol plus the Drive subset (`fakeDrive.ts`, #149), the Dropbox subset (`fakeDropbox.ts`, #150), the Graph subset (`fakeGraph.ts`, #151; its pre-signed URLs carry the real Microsoft host as `/ms/<host>/…`, which must pass the production allowlist, #202) and the pCloud subset (`fakePcloud.ts`, #211: its own consent page, both regions, `result` codes in 200 answers, content hosts checked against the production allowlist). The live suite (`pnpm test:live`) checks token refresh and the Drive, Dropbox, OneDrive and pCloud backends.
- The quota checks measure the home before the operation and do not reserve its bytes (only tus uploads reserve), so two copies or restores started at the same moment can together pass the quota by up to one of them. Largest folders come from the name index, so changes made on disk outside the app show only after the rebuild command.
- Recent covers only the home; cloud sources do not add their provider's recent files yet (left out of #149–#151, whose scopes do not list it). A row whose file was changed outside the app (not through it) stays until that path is written, moved or deleted through the app.
- A duplicate scan's result lives in memory until the next scan or a restart (the home's hashes stay cached in `content_hashes`). It compares a cloud only by the hash its provider lists, so a home file and its copy in a cloud are never one group, and a SharePoint file with only a quickXorHash is compared only with others of that algorithm. Batch rename works in one folder of one source; it is not offered in search, smart folder or tag views.
- tus uploads can target only `home`; a cloud or shared target needs its own placement (and, for a share, a decision on whose quota pays) (#152).
