# DESIGN

The design guide "Daylight Instrument" (`docs/design-guide.md`) is binding. This file records only what the guide does not cover and where this app deviates.

The rendered `design-guide.pdf` has recipes that `docs/design-guide.md` does not spell out: the data table (p.15), toasts (p.16), alert banners (p.17), the dropdown menu (p.18), tabs and the segmented control (p.19), progress bars (p.20) and empty states (p.27). Files follows them; see "Toasts, menus, segmented control and pills" below (#241). Where a section further down says "the guide has no recipe", it means there is none in either form.

## Tokens

`web/src/styles/tokens.css` and `web/src/styles/components.css` are copied from the guide bundle (`tokens.json` is canonical there). Do not edit values here; update the bundle and copy again. Fonts (Inter, IBM Plex Mono) come from `@fontsource` packages and are served by the shard, never from a font CDN.

## Icons

Line icons are SVG on a 24px grid with a 1.5px stroke, stored as data-URI custom properties (`--icon`) in `web/src/styles/app.css` and drawn through a CSS mask on the `.icon` class. The colour therefore comes from the theme tokens, not from the SVG. No emoji, no icon fonts. A provider is never shown by its brand logo: each "Connect …" button in "Cloud accounts" carries the line cloud, and pCloud's carries the cloud with a line "p" in it (`icon-provider-pcloud`, #211).

## Dialogs

The guide has no dialog recipe. `<AppDialog>` (`web/src/components/AppDialog.vue`) is a `.fs-sheet`-like surface (surface tone, hairline border, sheet radius, no shadow) with Calendar's modal anatomy (#244): the title sits over a `--border` hairline, and the action row under one; the X beside the title is optional (`closeLabel`, used by the details drawer). It is centred on a flat scrim of `--bg` at 80 % with no filter (#243; Calendar's 55 % plus `grayscale(.5)` left the page too readable, and a filter is a glass effect the guide rules out). The scrim separates the sheet by tone, not by elevation, so the "no shadows" rule holds in both themes. On phone width the sheet sits at the bottom edge and the action buttons share the row. A dialog taller than the window scrolls on its scrim with its head (title and hairline) held at the top of the window, on the sheet's own tone, so the member always sees what the dialog is (#236 P12); the drawer and the wide sheet scroll inside themselves. Actions are outline buttons of equal weight: the one forward action takes the amber hairline (`.button.primary`), a destructive one the danger hairline (`.button.danger`). Every action row is right-aligned and ends in the forward action (#238). In the collision dialog the order is "Skip", "Replace" (destructive), "Keep both": "keep both" is the forward action and takes the initial focus, because it never loses data. `ConfirmDialog` follows the guide's confirm dialog (PDF p.13): "Cancel" on the left with the initial focus, the destructive action on the right. The "apply to all" checkbox is a checkbox in the guide's box (see "Checkboxes" below).

## Selection, menus and drop targets

The guide has no recipe for selection or drop targets. A selected row takes a teal tint (`--data` at 9 %), never an amber fill, because amber is reserved for the one forward action. Row checkboxes are the guide's box, like the dialog checkbox (see "Checkboxes" below). The row action menu is the guide's dropdown (PDF p.18): a sheet-like popup (surface tone, hairline border, tile radius, no shadow) behind a borderless icon button with a line "more" icon; on phone width the button is a 44 px touch target and the row is checkbox, name, menu, with size and date on a second line. A drop target (folder row or breadcrumb) gets a dashed teal hairline. While items are marked for moving or copying, "Move here"/"Copy here" is the forward action (`.button.primary`) and "Move to trash" the destructive one (`.button.danger`).

## Sidebar and trash

The guide has no navigation recipe; the sidebar follows Calendar's (#244). It is a 240 px column on the surface tone with a hairline border, in three groups, each under a `.fs-label` title with a `--border` hairline between them: "Places" (My storage, each cloud connection, Cloud accounts), "Collections" (Favourites, Recent, Shared with me, My shares, File requests, Trash) and "Manage" (Storage usage, Members for the admin, Settings, Move to the shard). Entries carry a line icon, and the current place is marked by a straight 2 px teal bar at its left edge (the entry's left corners are square, its right corners keep the control radius) and teal text, never a fill. A source's entry ("My storage", a cloud connection) stays current in every folder of that source. On phone width it collapses behind a "Places" toggle under the header (see "Header, phone sidebar, keyboard help and touch targets"). The trash view reuses the file-list table; each row has "Restore" (outline) and "Delete permanently" (danger hairline). "Empty trash" is a danger outline button, dimmed when the trash is empty. Every permanent delete asks first in `ConfirmDialog`, where "Cancel" takes the initial focus, because the safe choice should be the default. The Recent view (line clock icon) reuses the same table with name, location, changed time and one outline "Open folder" link per row; the name is a bare link to the same place, and both open a file's folder with the file selected, as from Favourites (#235); an image, video or PDF shows its thumbnail in the folder list's 28 px slot (#244); its empty state is a muted sentence of its own, never the folder's.

A folder's location is written one way in every list, the search and the drawer (#244, `web/src/location.ts`): the root's name, then the folders, joined by " › " ("My storage › Projects", "Dropbox › Reports"), never a path with a leading slash. A cloud is named by its provider; its account is shown apart, muted, where the source itself is named (the root crumb, the search group).

## Upload panel and drop zone

The guide has no recipe for transfer lists; its progress bar (PDF p.20) is the 3 px line below. The upload panel is a sheet (surface tone, hairline border, sheet radius, no shadow) in the page column: in a folder under the toolbar, so the folder's title stays put when an upload starts, and on every other view at the top of the main area, so it stays while the member navigates and never covers the list (#239). The head is a small heading in the UI face, "Uploads · 1 of 4 · running", where the state is "running" while anything waits or runs, "paused" while only paused files remain and "finished" otherwise (#242). Each file is a row: the name, its state (a figure such as "42 %" in the mono face, a word such as "Waiting", "Uploaded" or "Failed" in the UI face), its actions, and a 3 px progress line under it, teal (`--data`) on a `--border-cool` track (#242; `--border` all but vanished on the dark ground), with no fill animation and no glow. The percentage is floored and stops at 99 % until the file is done, so it never claims more than was sent. A failed row turns its state text and line to `--danger` and says only "Failed"; the reason is in the failure summary, one box with a danger hairline: a count, the list "name: reason" and "Retry all" as the panel's one forward action (`.button.primary`). A row's pause, resume, retry and cancel are 32 px borderless icon buttons (line icons in `--line`, named by their `aria-label`) at the row's right edge, on the name's line; on phone width they are 44 px and the state takes its own line under the name. Text buttons are only in the head ("Clear finished") and the summary. "Upload" stays the toolbar's forward action, and "Upload folder" next to it is a plain outline. Files dragged in from the desktop mark the folder area with the dashed teal hairline of a drop target and show a one-line hint in `--line`.

The transfer panel (#152) is the same sheet at the top of the main area, with the same row recipe: one row per job ("Copy “name” to My storage/folder"), its state (the running figures "3 of 5 · 1.2 MB" in the mono face; "Done", "1 of 5 failed", "Cancelled" in the UI face), and the 3 px teal line over the settled items (floored, 99 % at most while the job runs, as on the migration page; #242). A job that ended with errors turns its state and line to `--danger` and lists the failed items with their reasons under its row in the small size, in `--danger`. Cancel is a danger outline while the job runs; "Clear finished" in the head is a plain outline. There is no forward action: the paste that started the job was it. A job of several items is labelled by their count ("Copy 2 items to My storage/folder"), with the names behind a native "Show names" disclosure in the small muted size (#234). An ended job has "Remove" (plain outline) instead of Cancel. Five seconds after the panel has shown an ended job on a visible page, a completed or cancelled one leaves by itself (on the server too); a failed one and a migration (whose page offers the cleanup) fold into one muted line, "One transfer ended · one with errors", with "Show"/"Hide" (`aria-expanded`) as a plain outline, and stay until removed.

## Migration

The guide has no wizard recipe. "Move to the shard" is the last entry of the sidebar's "Manage" group with a line icon (a cloud over a downward arrow onto a line). The wizard is one column up to 720 px with one step at a time under a numbered heading ("1. What to move"), which takes the focus when the step changes. The account is a native radio group tinted with `accent-color: var(--data)`. A folder is picked in a hairline box: the crumbs in `--line` (the current one in `--ink`) over a list of folder buttons with the folder line icon, separated by hairlines, 44 px high on phone width; opening a folder chooses it, and a sentence under the box says what was chosen. "Next" and "Start migration" are the forward action (amber hairline), "Back" a plain outline. The review is the details drawer's facts grid (from, to, files, folders, size) with "Counting …" or "at least" as a muted status line. The job's page uses the same column: the facts grid with the state in it, the 3 px teal progress line of the transfer panel, then "Summary" (verified files, size, failed), the failures in the panel's small `--danger` list, and "Export summary (CSV)" as a plain outline. "Delete verified originals …" is a danger outline under "Originals in the cloud", and it opens `ConfirmDialog`, where "Cancel" takes the focus. The cleanup's state and progress line follow under the same heading. On phone width the action buttons take the full row.

## Preview overlay

The guide has no viewer recipe. The preview is an `<AppDialog>` with `wide`: the same sheet, up to 1100 px wide and at most the viewport high, with the content scrolling inside and the actions always in view. On phone width it fills the screen apart from the scrim margin, and Previous, the position ("2 of 5", mono face, muted) and Next take their own row above Download and Close. Previous and Next stay focusable at the ends and are dimmed (`aria-disabled`), so the focus never drops out of the dialog. Images and video are contained to the sheet with the tile radius, in a `--bg` well with the tile radius and a 12 px margin, so a photo never sits on the white sheet (#242). Opened from the gallery, an image steps through the folder's images only, so the position ("2 of 3") counts photos; opened from the list, or a non-image opened from the gallery, it steps through every file. Text sits in a `--bg` well with a hairline border in the mono face, and Markdown is set at a 72-character measure with links in `--line`. For an unsupported type or a failed preview, Download becomes the forward action (`.button.primary`). A PDF page is drawn on white with a hairline border in both themes, because it is a printed page and its own colours assume paper.

## Thumbnails and gallery

The guide has no media grid. A list row shows a 28 px thumbnail with a 4 px radius in place of the file icon. A PDF's thumbnail is its first page, mostly white, so it takes a `--border-cool` hairline drawn inside its edge in the list and the gallery, like the preview's page (#236 P6); a photo has none. The gallery is a grid of tiles at least 160 px wide (104 px on phone width): each tile is surface tone with a hairline border and the tile radius, a square image cut to fill (`object-fit: cover`) on `--bg`, and the name in one line under a hairline, cut in the middle so the end and the extension stay ("Sonnenuntergang am…ilie.png", see "Responsive lists and names"). A file without a thumbnail, and a folder, show their line icon at 40 px in the same square. Hover turns the hairline teal (`--line`); there is no shadow and no zoom. A selected tile (#229) takes the list's selection tint (`--data` at 9 %) and the teal hairline. Its checkbox (top left) and menu button (top right) sit on small surface chips with a hairline over the thumbnail; they appear on hover, on focus and on a selected tile, and always on a touch screen (`hover: none`), where they are 44 px targets. The "List / Gallery" toggle is the guide's segmented control (see below).

## Buttons, rows and links

These follow Calendar's rules (#238).

- **Height.** A button is 36 px high, like a `.fs-input` field, so a field and its button align in one row (44 px on phone width, see above).
- **Hover and press.** A plain button takes the `--bg` ground and an `--ink-muted` hairline under the pointer; the forward and the destructive action keep their hairline and take an 8 % tint of their own colour. A pressed button rests on `--ink` at 6 %. Border and ground change over 0.15 s (the motion note in `tokens.json`). A dimmed button does not answer.
- **Focus.** A button shows the teal ring for the keyboard only (`:focus-visible`), never after a click. A label that wraps a hidden file input ("Upload") shows the ring of its input.
- **Rows.** A list row under the pointer takes `--ink` at 3 %; a selected row keeps its teal tint.
- **Links.** A link in running text is teal (`--line`) without an underline, underlined on hover. Links in rendered Markdown keep their underline, since they sit inside text the member did not style. A link styled as a button ("Open", "Open folder") is a button in every list.
- **Weight.** Revoking an app password is a danger outline, like "Remove access", since it ends access and asks first.

## Toasts, menus, segmented control and pills

These follow the PDF recipes (#241).

- **Toast (p.16).** The feedback of an action in a folder is a toast at the bottom right of the window (full width less the margin on the phone): surface fill, hairline border, tile radius, no shadow, and a 3 px left edge. The edge is teal (`--data`) for a success and `--danger` for an outcome with failures, such as "0 of 1 copied". A close X sits in the toast's bottom-right corner. A success fades after 5 s; an error stays until it is closed or replaced, and its details stay in the failure box above the list. The text is the page's `role="status"` live region, and an empty toast has no chrome and no size.
- **Dropdown menu (p.18).** The item menu lists what opens or looks at the item first ("Download", "Share", "Details"), then what changes it ("Rename", "Move", "Copy", the favourite toggle). The destructive "Move to trash" comes last, in `--danger`, under a hairline. The active entry (hover or focus) rests on `--ink` at 5 %, never teal or amber.
- **Segmented control (p.19).** "List / Gallery" is one control: a shared hairline around both segments. The current segment takes the surface fill and a hairline of its own; the other is transparent with muted text. On phone width the segments show line icons (lines with dots, four squares) at 44 px width and keep their names as `aria-label`.
- **Status pill (data table, p.15).** A status, an access level or a role is an outline pill (hairline, pill radius, no fill) with a 6 px dot. The dot is teal for a working connection, `--danger` (also the text) for one that needs signing in again and for an orphaned share, and `--ink-muted` where the pill only labels: "Can view", "Can edit", "Admin", and a connection that is unavailable or has no library yet.
- **Empty states (p.27).** Every view has its own empty sentence (#127). An empty folder is the guide's empty state (#240): centred in the column, a 48 px line glyph in `--line` (the folder glyph; a line upload glyph, an arrow onto a tray, at the root of "My storage"), one muted sentence and "Upload" as the forward action, which opens the toolbar's file picker. The root of "My storage" has its own sentence ("Nothing here yet. Upload your first files."). A read share shows glyph and sentence only. The other views keep their muted sentence without a glyph.

## Loading, error and not-found states

These follow the PDF's alert banner (p.17) and close the state review (#240).

- **Alert banner.** When a view's content cannot be shown (a folder that is not there or fails to load, `/me` failing, an unknown address, a public link that cannot be opened) it is replaced by one banner (`StateAlert.vue`): a danger hairline, `color-mix(in srgb, var(--danger) 7%, transparent)` fill, the control radius, a bold title in `--danger` (it is the page's heading), one sentence in `--ink`, and the one way on as the forward action: "Go to “My storage”" for something that is not there, "Try again" for everything else. A share that is gone for the member (revoked, or its item deleted by the owner) says "Share no longer available" with why, and its way on is "Go to “Shared with me”" (#235). A member who opens "Members" gets "Only for the shard’s admin" with "Go to “My storage”", without the admin's intro (#316). A folder in an error state has no toolbar, so nothing offers to upload into a folder that does not exist.
- **Refusals on the visitor's page.** "No downloads left" and a refused download are the same box (`.link-alert`, danger hairline and the 7 % fill) with the sentence in `--danger`. With no downloads left the page offers no "Download" and no "Open preview", only the refusal; a refusal is said once.
- **Row skeleton.** A list that loads with nothing in place yet (the first open of a folder, the trash, recent, favourites, shared) shows six rows at the folder list's row height (58 px, 77.4 px stacked), each with a glyph, a name and a figure bar in `--border`, with no shimmer, `aria-busy`, and "Loading …" kept as visually hidden status text. Moving from one folder to the next keeps the previous list in place, inert and dimmed under the loading note (#228).
- **Start.** While `/me` loads, the sidebar shows one `--border` bar per place and the page column says "Loading …". If `/me` fails (offline, a server error), the shell stays: header, sidebar with the places, and the alert banner in the page column. The member's own parts (cloud accounts, "Members", search, the header buttons) wait for `/me`.
- **Unknown address.** An address the app does not know shows "Page not found" in the banner, with "Go to “My storage”", and keeps the address.

## Type scale and page grid

These follow the guide's scale and Calendar's grid (#239).

- **Scale.** A view's title (`.view-title`) is h2 (20 px, 600). A section heading on a page (Settings, Storage, the migration steps, "Add a cloud account") is h3 (16 px, 600). The small heading inside a dialog or the drawer ("Who has access", "Versions") stays at the small size, 600. A dialog's title stays h3.
- **Folder title.** In a folder the current crumb is the title: h2, 600, in `--ink`. The crumbs before it are small and teal (`--line`), on the same baseline.
- **Mono.** The mono face is for figures only: sizes, dates, counts, progress and addresses (the list's size and date columns, the drawer's size and modified date, the versions' date and size, the visitor page's size, expiry and downloads, an upload's "42 %", a running transfer's "3 of 5 · 1.2 MB", Storage usage's breakdown and the sizes inside its usage sentences, #317). A size below a kilobyte names its unit in full ("25 bytes", "1 byte", "25 Byte", #315), the others by symbol ("2.5 kB"). A word is set in the UI face, also in a figure column ("No storage limit") and in a state ("Waiting", "Uploaded", "Failed", "Done").
- **Fields.** Every field has a `.fs-label` (uppercase, 10 px, muted) above it. A hint sits under the field in the small size and `--ink-muted` and describes it (`aria-describedby`), never in the placeholder. Only the header search and the member picker in the share dialog keep a placeholder; it prompts the typing and carries nothing the member needs to read later. A field error is the small size in `--danger`, 4 px under its field, 16 px above what follows.
- **Page column.** Every view of the signed-in app sits in one page column (`.page`) up to 960 px wide, left-aligned 24 px from the sidebar (16 px on phone width), like Calendar, so no gap opens beside the sidebar on a wide screen. Forms (Settings, the migration wizard and its job page, "Save shared files") use a 720 px column on the same edge (`.page-narrow`). The visitor's share page and the signed-out page have no sidebar and keep their own centred column.
- **Header.** The app name takes the sidebar's width, so the search field starts on the page column's edge; the member's name and the header buttons sit at the right end.
- **Upload panel.** It is a sheet within the column (its padding inside its width), under the folder's toolbar; see "Upload panel and drop zone".
- **Selection bar.** While a selection exists, the bar takes the place of the toolbar's actions, right-aligned like them, and opens with the count ("2 selected", small, muted). The list below never moves. On the desktop the toolbar holding the bar is sticky at the top while the list scrolls (#224); on phone width the bar stays the sheet fixed at the bottom.
- **List sheet.** The file list's table is a sheet with the 14 px sheet radius. Its borders are separate (row hairlines on the cells), since a collapsed table drops the radius; the corner cells round their own ground to match.

## Responsive lists and names

These close the table and truncation review (#237). The guide's data table (PDF p.15) has no narrow form; Files folds it into rows.

- **Stacked rows.** The folder list takes the phone's rows up to 900 px: no header row, checkbox, name, star and menu on the first line, size and date under the name (the sort menu stands in for the headers). The lists with buttons in their rows (trash, recent, favourites, shared, members, cloud accounts, app passwords, storage) need about 890 px of page for their columns, so they stack up to 1200 px: the name, then the location, then the figures, then the buttons under the name's text at their own width. On the phone the buttons share the row, as before. Above 1200 px the trash's two buttons stand one over the other at equal width in their cell: side by side, the German "Wiederherstellen" and "Endgültig löschen" would push the table past the 960 px page column (#309).
- **Names.** A name column keeps at least 12rem. A name breaks between words only (a single word longer than the line still breaks) and stops after two lines with an ellipsis; the full name is its `title`. Spaces show as typed (`white-space: pre-wrap`, #236 P1), so "a   b" never reads as "a b"; `pre-wrap` rather than `pre` keeps the two lines. On the phone the name's 44 px touch target is padding around the text, so a two-line name pushes its size line down instead of covering it.
- **One-line values.** A location ("Original location", "Location") is one line with an ellipsis, up to 16rem wide and down to 6rem when the name needs the room; an e-mail on the members page and a cloud account in the sidebar are one line with an ellipsis too. Each carries its full value as `title`. Table headers never wrap.
- **Sidebar connection.** The provider is the main line in ink; the account is the muted 11 px line under it, then the library and a status that is not "ok".
- **Members.** Amount (6em), unit and the buttons stay one row; an invalid amount's error sits under the row, is announced (`role="alert"`) and describes the field, which is `aria-invalid` (#236 P15). On stacked rows the form folds under the name and figures and may wrap on the phone.
- **Upload panel.** The name column keeps at least 8rem; on the phone the state takes its own row under the name, and the icon buttons stay at the right of the name (#242).
- **Gallery.** A tile's name is cut in the middle: the head takes the ellipsis, the tail keeps the extension and the four characters before it (`nameParts` in `web/src/format.ts`), so names that differ at the end ("Urlaub 01.png", "Urlaub 02.png") stay apart. The tile's accessible name is the whole name.

## Contrast, checkboxes and the usage bar

These close the contrast and dark-mode review (#243).

- **Control boundary.** Fields (`.fs-input`, also the selects), outline buttons and checkboxes draw their edge in `--border-control`: #788e95 in light (3.4:1 on the surface, 3.1:1 on the paper) and #7a6c55 in dark (3.3:1 and 3.6:1), so every control's boundary reaches the 3:1 of WCAG 1.4.11. Sheets, tiles, rows and separators keep the `--border` and `--border-cool` hairlines; they are not controls. See "Deviations".
- **Checkboxes.** Every checkbox is the guide's box (PDF p.9): the native input with `appearance: none`, 18 px, radius 5, a 1.5 px `--border-control` outline on a transparent ground; checked, it fills `--data` with a check in the surface tone. It stays a native input, so keyboard and screen-reader behaviour are unchanged, and the dark theme no longer shows the browser's grey filled square. Radios stay native, tinted with `accent-color: var(--data)`; they draw an outline circle in both themes.
- **Usage bar.** The gauge's track is `--border-cool` (the dark `--border` was 1.5:1 on the ground), 6 px high. Any usage fills at least 2 px, and the percentage sits beside the bar in the mono face and muted ink ("12 %", "< 1 %" for a sliver), as on PDF p.20. The meter keeps its figures as its accessible text; the percentage is for the eye only.

## Deviations

- **Light-theme contrast.** The guide's light `--ink-muted` (#6b7d82) and `--accent` (#c8761f) stay below WCAG AA 4.5:1 for small text on the paper and surface tones (3.9:1 and 3.2:1; table headers, sizes, dates, notes and the forward action's label are all small). `app.css` darkens them along their own hue in the light theme only, to #5a6b70 (5.1:1 on paper) and #9f5c16 (4.8:1). The dark theme's values pass and are unchanged. `tokens.css` keeps the guide's values, so the guide can take these over in its next version. #243 asked whether #a8641a, a less brown amber, could replace #9f5c16: it reaches 4.6:1 on the surface but only 4.2:1 on the paper, so #9f5c16 stays. Proposed for the guide bundle (`tokens.json` v0.2), so Calendar shares it: light `--ink-muted` #5a6b70 and `--accent` #9f5c16.
- **Control boundary.** The guide's `--border-cool` (#b7c7cd light, #473f31 dark) is 1.6–1.8:1 on paper and surface, below the 3:1 WCAG 1.4.11 asks of a field's or a button's edge. `app.css` adds `--border-control` (#788e95 light, #7a6c55 dark) for fields, selects, outline buttons and checkboxes (#243). The issue's suggested #8fa3aa and #6b604c stay under 3:1 (2.4–3.0), so both were darkened further along their hue. Proposed for the guide bundle as a new token, with `.fs-input`, `.fs-btn` and `.fs-check` using it.
- **Dialog scrim.** The guide has no dialog; Files uses `--bg` at 80 % without a filter (see "Dialogs"). Proposed for the guide bundle as the one scrim for both apps.
- The file list is a table (`FileList.vue`, a real `<table>`), because name, size and modified date are columns the user compares. The guide has no list recipe.
- **Native inputs for checkboxes and radios.** Files draws the guide's `.fs-check` box on the native checkbox (`appearance: none`, #243) instead of an `aria-checked` element, and keeps the native radio tinted with `accent-color: var(--data)` instead of `.fs-radio`. Both keep native keyboard and screen-reader behaviour without extra script. The checkbox's empty outline is `--border-control`, not the guide's `--border-cool`, for 3:1 (see "Control boundary").
- **Button height.** The guide's `.fs-btn` recipe sets only padding (`9px 16px`, about 33 px high). Files sets the height to 36 px with horizontal padding only, like Calendar, so buttons and fields line up (#238). It is a minimum height, so a label that wraps on a narrow screen grows the button instead of spilling out.
- **No focus scale.** The guide's `.fs-focusable` adds `transform: scale(1.2)` to the teal focus ring. Files shows the ring only. Most of its focus targets are full-width table rows, where the guide itself says to drop the scale. A scaled button or tile would cover its neighbours in the dense toolbar and the gallery. The ring alone (2 px `--line`, offset) is the same in every place.
