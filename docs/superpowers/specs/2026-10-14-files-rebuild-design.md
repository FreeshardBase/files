# FreeShard Files — rebuild design

Status: draft for review · 2026-10-14 · decisions by the shard owner, design by Claude

## 1. Why a rebuild

The current code (tagged `archive/gemini-2026-10-14` when the rebuild starts) was produced by an unsupervised agent pipeline. 85 issues were closed by that pipeline without independent verification. The external review (#91–#108) and a second audit (#109–#127) are open and unfixed. A third review found more of the same class:

- **Unauthenticated host-level file read and write.** `/wopi/tokens` takes `userId` as a path segment and does not validate it.
- **Anonymous access to the files API.** `/api/files` is reachable without login and falls back to a shared `default-user`.
- **Path traversal.** tus, sync, auto-filing, versioning and file requests build paths with `path.join` and never check the user root.
- **Remote code execution.** File names are passed to `tar` as arguments.
- **Symlink check does nothing.** It is dead code.
- **Broken core features.** Folder ZIP download fails, trash cleanup never frees disk space, and S3 and OneDrive do not work.
- **Simulated features.** OCR, malware scan, transcription, sync, backups, federation and vaults only pretend to work.
- **Untrustworthy tests.** Many tests have no teeth, and some write into the developer database.

The foundations are what is broken: auth, paths, persistence, storage and tests. Patching would inherit every one of them. The rebuild keeps the repository, its history and its issues, and replaces the tree.

## 2. Product

**What it is.** Files is a multi-cloud hub for the people of one shard: the owner (shard admin) and members, such as a family or a small team. It gives one interface over the shard's own storage and the cloud accounts each member connects. FreeShard's message is leaving big-tech clouds, so moving data onto the shard is a first-class flow.

**Cloud model.** Cloud files are shown **live**. Listing, preview, download and upload go straight to the provider. Nothing is mirrored onto the shard unless the user explicitly copies or migrates it. There is no background two-way sync, so there are no sync conflicts.

**Ownership.** Each member connects their own cloud accounts, and only that member sees them. Sharing works the same way for local and cloud files.

Legal hold, the "E2E vaults", malware scan, OCR, media transcription, full-text content index, federation across shards, presence, bandwidth throttling, the PDF and image editors, WOPI/Office editing, auto-filing and automation rules, webhooks, PATs, smart folders, tags, comments, file requests, the duplicate finder, the bitrot scanner, the failover provider, branding, S3, MOVEit, the outgoing WebDAV client, Paperless and Immich hand-off, dual-pane view and browser-style tabs.

## 3. Architecture

```
web/      Vue 3 + TS + Vite + Pinia + Vue Router   (SPA, built to static assets)
server/   Node 22 + TS + Fastify + Zod + better-sqlite3
shared/   TS types + Zod schemas used by both (API contract, error codes)
```

The repo is a pnpm workspace. The server serves the built SPA. It runs as one container, non-root, and a volume holds `data/` (database, user homes, thumbnail cache).

### 3.1 Identity and access

- **Login.** The only way in is the shard's OIDC provider (`{{ oidc.* }}`, the same model as calendar #331). The flow is authorization code + PKCE. `state`, `nonce` and the verifier come only from the server session. A missing or mismatched value is rejected.
- **User IDs.** Each person gets a stable internal user id, mapped from (`iss`, `sub`). Nothing is ever keyed by the `sub` string itself, by display name, or by `X-Ptl-Client-Id`. The `admin` role comes from a claim.
- **Sessions.** Stored in SQLite. They survive restarts and can be revoked.
- **App passwords.** Used for WebDAV. They are hashed with argon2id (`@node-rs/argon2`), shown once, and stored with a prefix so lookup does not need a hash scan.
- **Deny by default.** A global hook requires a session. Public routes are an explicit allowlist: `/s/:token/*`, the OIDC callback, `/healthz`, static assets.
- **CSRF.** Mutating requests must pass an `Origin`/`Sec-Fetch-Site` check and carry a double-submit token.
- **No local accounts and no auth bypass.** Development, tests and E2E sign in through a small fake OIDC provider (`server/test/support/fakeIdp.ts`) using the real login flow. The issuer may be `http://` only for `127.0.0.1` or `localhost`; any other `http://` issuer is refused at startup.
- **Fail fast.** At startup, Zod validates the config (session secret, encryption key, OIDC issuer, client id and secret, public URL). Anything invalid stops the process with `exit(1)`. There are no fallback defaults.

### 3.2 Storage

All file access goes through one interface:

```ts
interface StorageBackend {
  list(path, cursor?): Promise<{ entries: Entry[]; next?: string }>
  stat(path): Promise<Entry>
  read(path, range?): Promise<{ stream: Readable; size: number; etag?: string }>
  write(path, stream, { size?, ifMatch?, onCollision }): Promise<Entry>   // streaming / upload session
  mkdir(path); move(from, to, opts); copy(from, to, opts); delete(path)  // delete → trash
  quota(): Promise<{ used: number; total?: number }>
  thumbnail?(path, size): Promise<Readable | null>
  revisions?(path); restoreRevision?(path, id)
  search?(query): Promise<Entry[]>
}
```

**LocalBackend.** Every path goes through `resolveInRoot(root, userPath)`, which:
- rejects NUL bytes, control characters, `..` segments and absolute paths;
- normalises the path;
- `lstat`s each existing component and rejects symlinks;
- `realpath`s the deepest existing ancestor and checks that it lies under the root, with a trailing separator.

Writes go to a temporary file in the same directory, are `fsync`ed and then renamed. That is the one piece of logic carried over from the old `providers/local.js`. No other code builds filesystem paths. The trash and versions live under `<root>/.files/` and use the same resolver.

**Cloud backends.** `GoogleDriveBackend`, `DropboxBackend` and `GraphBackend` (one implementation for OneDrive and SharePoint drives) share an `OAuthClient`, which handles:
- token refresh on 401 or on expiry;
- writing rotated refresh tokens back immediately (encrypted with AES-256-GCM using the `ENCRYPTION_KEY` from config);
- backoff on 429 and 5xx, honouring `Retry-After`, with jitter.

Uploads use each provider's resumable upload session (Drive resumable, Dropbox upload sessions, Graph `createUploadSession`), so size limits do not apply. Listing follows pagination to the end, or hands the cursor through to the client. Paths are resolved to provider ids and cached briefly.

**Memory.** No backend ever holds a whole file in memory. A lint rule bans `arrayBuffer()`, `Buffer.concat` on bodies and `readFile` in request paths.

### 3.3 Addressing and API

- A file is identified by `{source, path}`. `source` is `home` (own shard storage), `conn:<id>` (own cloud connection) or `share:<id>` (something shared with me).
- The API has one route family: `/api/v1/sources/:source/{list,stat,content,thumbnail,…}`, plus `/api/v1/{transfers,shares,trash,versions,favorites,search,me,connections,admin}`.
- Every route has Zod schemas for params, query, body and response. The OpenAPI document is generated from them.
- Errors look like `{ code: "FILE_EXISTS", params: {...} }`. Codes live in `shared/`, and the client translates them.

### 3.4 Transfers

Copies and moves between sources, folder copies and migrations are **jobs** stored in SQLite: a job row plus one row per item. Workers are in-process, run with bounded concurrency, and can be cancelled. At startup, any job that was running is resumed. Progress reaches the client over SSE, scoped to the user.

Moving between sources means copy, then verify (size, plus a hash where both sides have one), then delete the source. An item is only marked done after it has been verified. A job only reports "completed" if every item is done; otherwise it reports "completed with errors", with the list of failed items.

### 3.5 Sharing

- **Internal shares.** A share points at `{owner, source, path}` and grants `read` or `edit` to members. The recipient reaches the file through `share:<id>`. Every access is re-checked against the share row, and access to the owner's cloud goes through the owner's connection on the server.
- **Public links.**
  - Tokens come from 16 random bytes, base64url.
  - The password is hashed, and attempts are rate-limited per token and per IP.
  - An expiry that cannot be parsed is rejected when the link is created, not treated as "never".
  - The download limit is counted on the server for every byte-serving request.
  - Content is proxied through the shard.
  - The share page escapes all output and sends a strict CSP.
  - HTML, SVG and XML are always served as `attachment`.
- Shares that point at a deleted target or an unlinked connection go `orphaned` and return 410. They never fall back to another source (see #95).

### 3.6 Persistence

- better-sqlite3 in WAL mode.
- Migrations in `server/migrations/NNN_name.sql` are applied in order and recorded in `schema_migrations`.
- Every foreign key used in a lookup gets an index.
- Operations with several steps run in transactions: trash plus row, move plus share and favourite path updates, job state changes.
- There is a single data root, `DATA_DIR`. Every path is derived from it in exactly one module.

### 3.7 Errors, logging, hardening

- **No empty or swallowing `catch`.** A lint rule enforces it, and every exception to the rule needs a comment.
- **Typed domain errors.** They map to HTTP status and error code in one place.
- **Crashes.** `unhandledRejection` and `uncaughtException` are logged and the process exits; the container restarts it.
- **Logs.** pino, JSON. Query strings, `Authorization` headers and tokens are redacted.
- **Headers and limits.** `@fastify/helmet` headers (CSP, nosniff, frame-ancestors, referrer-policy). Body limits on JSON. Upload size and quota are checked before any upload is accepted.
- **Outbound HTTP.** The server only calls fixed provider hosts. There is no feature that fetches a URL the user supplies, so the SSRF surface is closed.

### 3.8 Frontend

- **Layout.** A source sidebar (Shard, the member's connections, "Shared with me", Favourites, Recent, Trash). The main area holds the file list, as a grid or a list, virtualised. A details drawer, a preview overlay, a transfer and upload panel, a share dialog, settings, and an admin page for members and quotas.
- **State.** Pinia stores, one per concern: session, sources, the current folder, selection, transfers, settings. All API calls go through a typed client generated from `shared/`.
- **Accessibility.** Every dialog uses the shared `<AppDialog>`: `role="dialog"`, `aria-modal`, a focus trap, focus restored on close, and Esc to close. The file list has roving tabindex and arrow keys; Enter opens, F2 renames, Delete moves to trash. `alert()` and `confirm()` are never used. Lint rules ban `v-html` and hardcoded user-visible strings.
- **Design.** Tokens from the design guide are imported as CSS custom properties. Any deviation is recorded in `DESIGN.md` with a reason.

### 3.9 Testing

- **Unit and integration tests (Vitest).** Each test file boots the real Fastify app on port 0, with a temporary `DATA_DIR` and a temporary database, and cleans up afterwards. Config is loaded with `NODE_ENV=production`; sign-in goes through the fake OIDC provider. Nothing ever touches `data/`.
- **Fake provider servers.** HTTP servers that implement the subset of the Drive, Dropbox and Graph protocol in use: pagination, 401 → refresh, rotated refresh tokens, 429 with `Retry-After`, upload sessions, and 302 for content downloads. Backends are tested against them.
- **Live provider tests (`pnpm test:live`).** They run when `LIVE_*` refresh tokens are present in an untracked env file. Without tokens they report skipped. They are never counted as passed.
- **Security regression tests.** Every finding in #91–#127 that still applies to the new design gets a named test. Each test is mutation-checked: removing the guard must turn it red.
- **E2E (Playwright, desktop and mobile).** Covers every UI feature: real file upload with `setInputFiles`, download content checks, drag & drop, the collision dialog, focus traps and keyboard paths. Includes screenshot baselines for the main screens in both themes and all three languages.
- **WebDAV.** `litmus` runs in a container against the server, and rclone does a round trip.
- **i18n.** Every key exists in every language. Deutsch (Du) and Deutsch (Sie) are checked for mixed address forms. Lint finds no literal strings.

### 3.10 Packaging

- Multi-stage Dockerfile on `node:22-slim`, running as a non-root user.
- Includes ffmpeg and the libvips that `sharp` brings.
- `.dockerignore`, a healthcheck, and a compose file with no code bind-mounts.
- The app template in `app-repository` is created interactively, not by the pipeline.
- The licence is the owner's decision (#108) and is asked before any public release.

## 4. Migration of the repo and the tracker

1. Tag the current `main` as `archive/gemini-2026-10-14`. Remove the old tree in one commit, then build the new skeleton.
2. Self-closed issues (#1–#86) each get a comment: "closed by the earlier pipeline without verification; superseded by the rebuild (spec link)", or "deferred until after v1, see spec §2.2 and the deferred tracker".
3. Open issues #87–#127:
   - Issues that still apply become acceptance criteria or regression tests for rebuild issues, and are linked from there.
   - Issues about a deferred feature (§2.2) are closed with label `deferred` and linked from the deferred-features tracking issue, so they stay findable.
   - The reviewer closes the remaining ones once the rebuild issue lands.
4. New issues are created from this spec, labelled `rebuild` and `phase-N`. #128 stays the tracker.
5. Local `data/` (the developer database, which has accumulated test pollution) is not touched without asking the owner.

## 5. Delivery

- **Phase B: foundation.** Done interactively: skeleton, config, auth, `resolveInRoot`, LocalBackend, migrations, error handling and logging, the test harness with a fake-provider scaffold, a Vue shell with tokens and i18n, and local gates (`pnpm typecheck lint test e2e`). Exit criterion: log in through OIDC against the fake IdP; then browse, upload and download in the shard home, fully tested.
- **Phase C: pipeline.** `vacation_framework/issue_driver.py` gains repo profiles (`--profile files`). The profile defines the suites, forbidden paths (plus `data/`, `*.db`, `.env*`), allowed tools, and the path to the CLAUDE.md. Gates: red/green on the declared tests, all suites green, typecheck and lint clean, and for UI issues, screenshots attached to the PR. Merge with `--merge squash` on local gates. The queue lives in `queue-files.txt`.
- **Phase D: autonomous.** The queue runs in this order:
  1. security regressions
  2. local core flows, ZIP download and Recent
  3. thumbnails and gallery
  4. sharing
  5. Drive
  6. Dropbox
  7. Graph
  8. transfers
  9. migration
  10. versions and favourites
  11. storage overview
  12. WebDAV
  13. PWA and Share Target
  14. polish (design, accessibility, mobile, i18n completeness)
  15. packaging

  Product questions that come up along the way are decided by Claude, recorded in `DECISIONS.md`, and noted on the issue. Only irreversible steps (deleting user data, the licence, a public release) are asked first.
