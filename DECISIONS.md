# DECISIONS

Dated decisions, newest last. The spec is `docs/superpowers/specs/2026-10-14-files-rebuild-design.md`; this file records what was decided after or beside it.

## 2026-10-14: rebuild in the same repo

The rebuild happens in this repository, so history and issues stay. The old tree is kept at tag `archive/gemini-2026-10-14` and is reference only.

## 2026-10-14: no local accounts, no bypass

There are no local accounts and no auth bypass. Development, tests and E2E sign in through a fake OIDC provider (`server/test/support/fakeIdp.ts`) using the real login flow.

## 2026-10-14: admin role from a configurable claim

The admin role comes from the claim named in `FILES_OIDC_ROLE_CLAIM` matching `FILES_OIDC_ADMIN_VALUE`. The claim that shard_core will send (freeshard#147-149) is not fixed yet, so it is configuration, not code.

## 2026-10-14: locale has no platform source yet

The platform preference for language does not exist yet (freeshard#168). `resolveLocale` takes the parameter once the source exists.

## 2026-10-14: deferred features in one issue

Features deferred by spec §2.2 are tracked in one issue labelled `deferred`, which links each to its old issue.

## 2026-10-14: deny-by-default is route-based

The guard decides on the matched route pattern (`req.routeOptions.url`), not on the raw URL. Review found that `/%61pi/...` bypassed a `startsWith('/api/')` check on `req.url`, because the router decodes the path. The SPA fallback likewise decides on the decoded pathname.

## 2026-10-14: `__Host-` session cookies

On https the cookies are `__Host-fs_sid` and `__Host-fs_login` (Secure, Path=/, no Domain). Sibling apps on the same shard domain could otherwise toss cookies into Files. Plain names are used only on http loopback, where browsers reject Secure cookies.

## 2026-10-14: returnTo is same-origin only

`returnTo` after login must be a same-origin path. Dot segments and `//` prefixes are rejected, and anything unparsable falls back to `/`. This closes open redirects through the login flow.

## 2026-10-14: inline content only from an allowlist

File content is served inline only for images (not SVG), video, audio, PDF and `text/plain`, always with `Content-Security-Policy: sandbox`. Everything else is an attachment. HTML, SVG and XML in a user's folder must never run in the app's origin.

## 2026-10-14: non-canonical names are skipped in listings

On-disk names that are not canonical (NFD-normalised, containing control characters, or invalid UTF-8) are skipped in listings. They cannot round-trip through the API's path rules, so showing them would offer entries the user cannot open.

## 2026-10-14: upload content-type gate before body parsing

The upload route checks the content type (`application/octet-stream`) in `onRequest`, before any body parser runs. Otherwise a JSON or text content type would make Fastify buffer the whole body in memory, which is a denial of service.

## 2026-10-14: TypeScript pinned to 6.x

TypeScript stays on 6.x until typescript-eslint supports 7. Lint is part of the gate, so the compiler cannot get ahead of it.

## 2026-10-14: pnpm 12 with `allowBuilds`

The workspace uses pnpm 12. Dependency build scripts are denied unless listed under `allowBuilds` in `pnpm-workspace.yaml`, so a new native dependency needs an explicit, reviewed entry.

## 2026-10-15: encryption key derived from a shard secret

The shard's app template can only fill in `{{ secret('…') }}` (32 characters of `[A-Za-z0-9]`), so `FILES_ENCRYPTION_KEY` takes any secret of at least 32 characters. Startup refuses a shorter one. The AES-256 key is derived with HKDF-SHA256, using salt `freeshard-files`, info `files/encryption-key/v1` and 32 bytes of output (`server/src/config.ts`). A base64 key from before this change is still accepted, but it is now treated as a secret and hashed, so it yields a different key. Nothing has been deployed and nothing has been encrypted yet, so there is no migration path. Changing the salt or info later would orphan encrypted refresh tokens and needs a versioned re-encryption.

## 2026-10-15: admin role claim is optional

shard_core's OIDC provider sends `sub`, `name`, `preferred_username` and `email`, but no role claim, so the app template cannot fill in `FILES_OIDC_ROLE_CLAIM` / `FILES_OIDC_ADMIN_VALUE`. Both variables are now optional, but only as a pair: setting one without the other refuses to start. Without them every login maps to `member` and admin-only features stay unavailable (least privilege). An earlier admin is demoted on their next login, because the role is written on every login. Guessing a claim or making the first user admin would grant rights the platform never asserted. Once freeshard#251 lands, the template sets the claim (`freeshard_role` = `owner`).

## 2026-10-15: startup sweep of upload temp files

Question: where does the sweep run, which homes does it visit, and how does it handle errors? It runs in an `onReady` hook in `buildApp`, because both `listen()` and `inject()` wait for that hook. No request can arrive before it finishes, and the test harness exercises the same path. It visits every directory under `homes/` (`paths.ts`), not only the users in the database, so a home whose user row is gone is cleaned too. It recurses into `.files/` as well, since temp files are swept wherever they sit. #140 must therefore not store resumable tus state under the `.<16hex>.upload` name. Only regular files that match exactly are removed; symlinks are neither followed nor removed. An unreadable directory or a failed unlink is logged at warn with the home id and the home-relative path, and the sweep goes on. A sweep failure does not stop startup, because a leftover temp file only wastes disk space. The info line carries only the counts `removed` and `failed`.

## 2026-10-15: start as root, chown only `/data`, drop to uid 1000 in Node

On a shard the Docker daemon creates the `/data` bind mount as root, and the image used to run as `node`, so Files could not write there. `user: 0:0` in the app template would run the whole server as root, so the image now has no `USER`. `main.ts` checks whether it is uid 0. If it is, it chowns `/data` to 1000:1000, plus any parents it had to create, and never recurses into existing contents. Then it calls `setgroups`/`setgid`/`setuid` and verifies the drop, all before the database or any route exists. Doing this in Node rather than in a shell entrypoint with `gosu`/`setpriv` adds no package. It keeps one process as PID 1, so SIGTERM handling is unchanged, and the steps can be unit-tested (`server/test/dataDir.test.ts`). A container started as a non-root user skips the root step. Either way, startup then checks that `/data`, `files.db` and `homes/` are writable, and exits 1 naming the path if they are not. Leftovers owned by root from an earlier root run need a one-time `chown -R` on the host. Chowning them on every start would be slow on large trees and would silently rewrite ownership of user data.

## 2026-10-15: login-error cleanup, concurrent migrations, keep-both names (#134)

Question: when does the SPA drop `?loginError=1`, what does a second process do with a migration that another one is applying, and what does "keep both" do with an extension that does not fit?

The SPA drops the flag only after `/api/v1/me` has answered. The 401 handler skips the login redirect while the flag is in the URL, so dropping it earlier would bring the redirect loop back. It uses `router.replace` (history replace, no reload).

Each migration is checked and applied inside one `BEGIN IMMEDIATE` transaction. A second process waits on the lock (`busy_timeout`), then finds the migration recorded, so both start. Failing loudly would also be safe, but it would turn a routine overlapping start, such as a restart, into a crash.

"Keep both" keeps `name (n).ext` within 255 bytes and cuts the stem at whole code points. If not even one character of the stem fits before the extension, the extension is treated as part of the name and the whole name is cut. Cutting the extension instead would make up a file type the original never had.

## 2026-10-15: one `resolveSource`, conditional and sized writes, one-trip reads (#135)

Question: what source ids are valid, what answers an unknown one, where is access checked, and what do the new `write` options `size` and `ifMatch` mean?

`resolveSource(req, source)` in `server/src/storage/resolveSource.ts` is the only place a source id becomes a backend and an access level. The grammar is exact: `home`, `conn:<id>` or `share:<id>` with `<id>` of 1–64 characters from `[A-Za-z0-9_-]`. Nothing is normalised, so `HOME`, `home:<userId>`, a bare user id, an empty id or an unknown prefix are all `SOURCE_NOT_FOUND` (404), never the caller's home (#95). A malformed id gets the same answer as an unknown one, so it reveals nothing about which ids exist. `conn:` and `share:` answer `SOURCE_NOT_FOUND` until #148 and #146 fill them in. `home` is always the caller's own home with `edit`. Every source route resolves its source before it reads any input, and the mutating ones (`PUT content`, `mkdir`) answer `FORBIDDEN` (403) unless the access is `edit`. A framework 404 still maps to the generic `NOT_FOUND`, because only `resolveSource` throws `SOURCE_NOT_FOUND`.

`ifMatch` is allowed only with `onCollision: replace` (otherwise `VALIDATION`): a conditional write replaces exactly the version the client saw, and "fail" or "keep both" would contradict that. A missing file or a different ETag is `PRECONDITION_FAILED` (412). The check runs before the body is read and again right before the rename, which narrows the lost-update window but does not close it, since there is no lock. The route takes it from the `If-Match` header and compares it as an exact string. `*` and weak tags are not supported, because no client sends them. `size` is the declared length. The route passes `Content-Length` when there is one. More or fewer streamed bytes are `SIZE_MISMATCH` (400), and the temp file is removed. A declared size above `maxBytes` is `PAYLOAD_TOO_LARGE` before any byte is read.

`read` returns the `Entry` with the stream and the ETag. The Range is resolved against the size of the file actually opened (a function range), so `GET content` needs one backend call. The old stat/read race on `Content-Range: bytes */<size>` cannot happen any more.

## 2026-10-15: collision dialog and `<AppDialog>` (#136)

Question: what do Esc, "apply to all" and "keep both" do, and how does the SPA find out about a collision without sending a file twice?

Esc (closing the dialog) counts as "skip" for the current item only. Closing must never overwrite anything or decide for items the user has not seen. The batch goes on, and the summary reports skipped items separately from failures (`upload.summarySkipped`). The scrim does not close the dialog on click, so a stray tap cannot skip a file.

"Apply to all remaining" is offered only when items follow. With "replace" or "keep both" for all, the remaining files are sent with that policy straight away. With "skip" for all, each one is still sent with `fail` first, so a file whose name is free is uploaded as usual and only the taken ones are skipped.

The SPA always sends `onCollision=fail` first. `LocalBackend.write` now answers `FILE_EXISTS` with `{ name }` in `params` before it reads the body, and the route closes the connection on any rejection that leaves the body unread. The SPA sends the file a second time only after the user has chosen. The hard-link in `place()` still catches a name that is taken between that check and the rename.

The first "keep both" name is `name (1).ext`, as the issue states, not `(2)` as before. Nothing has been deployed, so nothing depends on the old numbering. The dialog shows the name from the server's `params`, because the server decides which entry conflicts.

`<AppDialog>` is open while it is mounted. It makes every other child of `<body>` `inert`, sets `overflow: hidden` on `<html>`, traps Tab, and restores focus on unmount to `returnFocus` (for an upload, the upload button's input) or to the element focused before. It uses no native `<dialog>`, because `showModal()` lets Tab leave into the browser chrome and it would be a second code path to keep accessible. The lint config bans `role="dialog"`/`alertdialog`, a bound `:role` and `<dialog>` outside `AppDialog.vue`.

## 2026-10-15: rename, move, copy and delete in the home (#137)

Question: what does "replace" do to the old item, how are the filesystem and the database kept consistent, which path-dependent tables does the cascade cover, and how do keyboard and touch users reach the actions?

"Replace" never destroys anything: the existing target goes to the trash (with its trash row) in the same transaction as the move or copy. Moving an item onto itself is a no-op (200). A folder cannot be moved or copied into itself or a descendant (`TARGET_INSIDE_SOURCE`, 409), and "replace" is refused the same way when the target holds the source, because the source would go to the trash with it. Copying onto the item's own name is allowed and is how "duplicate" works: the collision dialog offers "keep both", which gives `name (1).ext`.

Every move and delete runs one `BEGIN IMMEDIATE` SQLite transaction around synchronous `rename`s. The renames are recorded and undone in reverse when anything after them fails, including the commit, so neither a ghost row nor a lost file is left (#117). The immediate lock also serialises concurrent moves and deletes from this app. Uploads do not take it, so a name check against a concurrent upload still has a small window (for files, `rename` would replace; this is the same window the upload's own hard-link closes for uploads). A batch delete is all or nothing: one missing path keeps every item in place, and the route answers its error. Items beneath another selected item go with it.

Copies are built in `<home>/.files/tmp/<id>` (files through `copyFile`, i.e. `copy_file_range` in the kernel, each file and folder fsynced) and renamed into place in the transaction, so a half-done copy is never visible. The startup sweep now also empties `.files/tmp/`, without following a symlinked `.files` or `tmp`. A symlink or special file inside a copied folder fails the copy with `PATH_SYMLINK`/`PATH_INVALID` instead of being skipped silently. Trashed items live at `<home>/.files/trash/<32hex>` with a `trash` row (original path, type, size, time); listing, restore and expiry are #138.

No path-dependent table exists yet (shares, favourites, the search index and versions come later). The cascade is the list `PATH_TABLES` in `server/src/storage/pathRefs.ts`: a move rewrites the rows of the item and everything beneath it (prefix match with `substr`, so `/a` never matches `/ab`), a delete or a replaced target removes them. Each issue that adds such a table appends it there and extends `server/test/transfer.test.ts`, which already asserts the cascade per table through the app for single delete, multi delete, replace and move, using two stand-in tables passed in through the harness.

UI: Space now toggles the selection of the focused row (it used to open a folder; Enter still opens), Ctrl/Cmd+click toggles, Shift+click selects a range, Ctrl+A selects all. F2 renames, Delete moves to the trash without asking (the trash makes it reversible, and `confirm()` is banned), Ctrl+C/X mark items and Ctrl+V pastes into the open folder. Marked items survive navigation; the selection bar then offers "Move here"/"Copy here" as the forward action, which is how an empty folder, the mouse and touch paste. Each row has an action menu (menu button pattern; also on right-click, the context-menu key and Shift+F10) with rename, move, copy and trash, so every action works on a phone without a keyboard. Drag & drop moves onto folder rows and breadcrumbs (desktop; touch uses the menu). The dragged payload is our own MIME type, so files dragged in from the desktop are never taken for a move.

## 2026-10-15: local trash, restore, permanent delete and expiry (#138)

Question: where does the trash live and what counts towards usage, how does restore treat a taken name or a vanished folder, what is "one code path" for permanent deletes, and how does the expiry job run?

The trash lives under the home (`<home>/.files/trash/<32hex>`, one `trash` row each), so trashed bytes count towards the member's usage until purged without any extra bookkeeping; the trash view shows the sum. A folder's row records the bytes of its whole tree, measured before the delete transaction. The API is `/api/v1/trash` (list), `trash/restore` (one item per request), `trash/delete` (ids) and `trash/empty`, with no source segment: only the home has a local trash, cloud deletes go to the provider's trash.

Restore takes the stored original path through the same resolver as any user path (a symlink or a file on the way is refused), recreates missing parent folders, and uses the move's collision rules: `fail` answers `FILE_EXISTS` and changes nothing (#111), `keep-both` gives `name (1).ext`, `replace` sends the taken item to the trash. The SPA asks with `fail` first and shows the collision dialog; Esc skips.

`LocalBackend.purge` is the only way out of the trash: single delete, "empty trash" and the expiry job all call it. Per item it removes the bytes first, then deletes the row and the rows hanging off it (`TRASH_TABLES` in `pathRefs.ts`, empty today) in one transaction. If the bytes cannot be removed the row stays, the error is logged with the trash id, and the item is reported as failed: the routes answer `PURGE_FAILED` (500) with the count, the job lists it in `failed` and retries next run (#102, #112). Bytes that are already gone count as removed, so a row without bytes can always be cleared. Restore and purge of one member take an in-process per-member lock, so a purge never removes bytes a restore is moving; the app runs as one process.

Expiry uses `deleted_at` plus `FILES_TRASH_RETENTION_DAYS` (default 30, 1–3650), so a changed setting applies to items already in the trash. The job runs once after the startup sweep and then hourly, skips a tick while a run is in flight, and is awaited on shutdown. Items whose row vanished meanwhile (restored) are skipped, not errors. A new index on `trash(deleted_at)` serves its query (migration 003).

Permanent deletes ask first in an `<AppDialog>` ("Cancel" has the initial focus); moving to the trash still does not ask, since it is reversible. The sidebar ("My storage", "Trash") is the start of the spec §3.8 source sidebar; on phone width it is a row of tabs under the header.

## 2026-10-15: folder and selection as a streamed ZIP (#139)

Question: what does the archive contain and how is it laid out, which ZIP features does it use, what happens when something goes wrong after the first byte, and how does a selection reach a `GET`?

`GET /api/v1/sources/:source/zip?path=…` takes `path` once (a folder, a file, or `/` for the whole source) or repeated (a selection). Up to 1000 paths are accepted; a selection longer than the URL allows is downloaded as its folder instead. Paths beneath another selected path come with it; whatever is left must share one parent folder (`VALIDATION` otherwise), because entry names are relative to that folder: a folder `/a/b` gives `b/…`, a selection gives its items at the top. The file is called `<name>.zip` for one item, `<folder>.zip` for a selection, and `files.zip` for the whole source or a selection at its top level. Each path is stat'ed before the first byte, so a missing path, a symlink or the internal area still answers a JSON error.

The writer (`server/src/storage/zip.ts`) is our own, about 150 lines, with no dependency. It walks only through the backend's `list` and `read`. So the archive holds exactly what a listing shows: no symlinks, no `<root>/.files/`, no upload temp files, no non-canonical names. Every path passes `resolveInRoot`, and the same code will serve cloud sources later. `.files` is internal only at the home root; a folder of that name deeper down is the member's own and is included. Entries are stored, not deflated. Most bulky content on a shard (photos, video) is already compressed, deflate would cost CPU on small hardware, and the CRC is computed as the bytes pass. Every file entry is ZIP64 from the start (sizes `0xFFFFFFFF` plus a ZIP64 extra in the local header, then a 64-bit data descriptor), because its size is only known once it has been read. A ZIP64 end record is always written. All names carry the UTF-8 flag. The only state that grows is the central directory, about 100 bytes per entry. There is no `Content-Length`, because a file may change while it is read.

Once the first byte is out, the status can no longer change. A failed read then aborts the response (Fastify destroys the socket and logs it) and no end record is written, so the client sees a failed download, never a short archive that looks complete. A client disconnect returns the generator, which destroys the open file stream. Nothing is written to disk, so nothing is left behind.

UI: the selection bar has a "Download" link. One selected file downloads as itself, anything else as a ZIP. The row menu has "Download" as its first item, so a folder downloads without selecting it first, also on a phone.

## 2026-10-15: resumable uploads over tus, quota, upload panel, folder upload (#140)

Question: which part of tus is offered and how is it addressed, where do the bytes and the state live, what counts against which limit, how does the collision dialog fit into a resumable upload, what does the panel do, and what happens to the plain `PUT content`?

The server speaks tus 1.0 under `/api/v1/uploads` (`server/src/routes/uploads.ts`), written here without a dependency: `OPTIONS` (discovery), `POST` (creation), `HEAD`, `PATCH`, `DELETE` (termination), and `Upload-Expires` on every answer (expiration). `Upload-Defer-Length` and creation-with-upload are not offered: the length has to be known up front, because size and quota are checked at creation. The target goes in `Upload-Metadata` as `source`, `path` and `onCollision` (default `fail`); other keys such as a client's `filename` are ignored. The source goes through `resolveSource` with `edit` access like every other write; today only `home` resolves. Every route needs a session, the mutating ones also Origin and the CSRF token, like every other route; `Tus-Resumable: 1.0.0` is required (412 otherwise). An id is 32 hex characters and is looked up together with the member, so another member's id, an unknown one and a malformed one all answer 404.

One row per upload in the new `uploads` table (migration 004) holds target, length, policy, expiry and `received`, the bytes that have been fsynced. The bytes collect in `<home>/.files/uploads/<id>`, reached through `resolveInRoot` like the trash; the name is not `.<16hex>.upload`, so the startup sweep leaves a paused upload alone. A `PATCH` truncates the file back to `received`, streams the body after it, then fsyncs and records the new size, also when the connection drops halfway, so the client continues with `HEAD` + `PATCH` from what is really stored. Only one request per upload runs at a time (`UPLOAD_LOCKED`, 423; in-process, since the app is one process). A wrong `Upload-Offset` is `OFFSET_MISMATCH` (409) with the stored offset. An upload expires 24 hours after it was created or last received bytes. An hourly job, started after the startup sweep like the trash expiry, removes the bytes and then the row (`server/src/storage/uploads.ts`) and skips an upload that is receiving bytes right now.

Limits. An `Upload-Length` above `FILES_MAX_UPLOAD_BYTES` is `PAYLOAD_TOO_LARGE`, one above the remaining quota `QUOTA_EXCEEDED` (507), both before a row or a byte exists. A client that sends more than it declared, by `Content-Length` or in a chunked body, is cut off with `SIZE_MISMATCH` and its whole upload is dropped (#113). The issue asks for "the member's remaining quota", but no quota existed, so `users.quota_bytes` is added (NULL = no quota, which is today's behaviour; the admin page that sets it comes with the storage overview). Usage is everything under the member's home, including the trash and staged uploads, plus what the member's other open uploads still have to send (a reservation), so two uploads cannot both take the last free bytes. The reservation check and the insert run in one transaction. Each `PATCH` checks again, so a quota lowered meanwhile stops the upload without storing more. The walk over the home only happens when a quota is set. The plain `PUT content` is held to the same quota, so it is no way around it. Copies are not checked yet (see CONCEPTS, *Known drift*).

Collisions. The policy comes with the creation, and `fail` with a taken name answers `FILE_EXISTS` before any byte is sent, so the SPA asks the #136 question first, as before. If the name is taken while the bytes are on their way, the last `PATCH` answers `FILE_EXISTS` and the complete upload stays. `POST /api/v1/uploads/:id/finish` with the chosen policy then places it without sending the bytes again; "skip" terminates it. `finish` is the one route that is not part of tus. Placement creates missing parent folders and renames or hard-links the staged file in the same transaction that deletes the row. "Replace" overwrites, like `PUT content` always has; versions on overwrite come with the versions issue.

SPA. `web/src/api/tus.ts` is our own small tus client: 8 MiB `PATCH` chunks, so a dropped connection or a buffering proxy loses at most one chunk, two automatic retries after 0.3 s and 1 s (each with `HEAD` first), then the item fails and waits for the user. The upload URL is kept in localStorage under target, size and modification time. Picking the same file again after a reload therefore continues where the server stopped; a browser cannot reopen a file by itself after a reload, so it has to be picked again. The uploads store runs one item at a time in pick order, because the collision question needs an answer before the next item starts. The panel sits above the page in the shell, so it stays when the member navigates, and it asks the collision question itself. Each item shows a progress bar and has pause/resume, cancel (which terminates on the server) and retry. Everything that failed is in one summary with one "Retry all" button, never one message per file and never `alert()` (#119). The status line still reports each pick ("2 of 3 uploaded") once all its items have an outcome; a paused item keeps its pick open. "Clear finished" removes finished items and terminates what the server holds of failed ones.

Folders. "Upload folder" is a second picker (`webkitdirectory`). Dropping files or folders from the desktop onto the folder view uploads them too, and dropped folders are walked through the entries API. Each file keeps its path below the chosen folder, and placement creates the folders. Empty folders are not recreated: the directory picker does not report them, and doing it only for drops would make the two ways differ.

`PUT /api/v1/sources/:source/content` stays for API clients and scripts; the SPA no longer uses it.

## 2026-10-15: the Recent view (#141)

Question: what counts as a recent entry, how many are kept, how do entries follow moves and deletes, what does a row open, and where do cloud sources fit?

An entry is the item a member placed through the app in their home: an upload (`PUT content` or a finished tus upload), the target of a copy, move or rename, and a restored item. `mkdir` is not a change to a file and is not recorded. A folder that is moved, copied or restored is one entry, not one per file inside it, so a large folder cannot push everything else out. Writing a path again moves its entry to the top instead of listing it twice. Each member keeps the newest 100 entries (`RECENT_CAP`), trimmed in the same statement batch as the insert; 100 fills several screens and keeps the table small. Rows are per member and the API answers only the caller's own; an activity feed of other members' actions is not in v1 (#22).

The `recent` table (migration 005) is the first entry in `PATH_TABLES`, so the #137 cascade rewrites entries on a move (including those beneath a moved folder) and removes them on a delete or a replaced target, in the move's or delete's transaction. The entry itself is written inside the same transaction as the write (for `PUT content`, right after the rename, since that path has no transaction around the rename). `UNIQUE (user_id, path)` keeps one row per path. A row can still point at a path that was changed outside the app; a move onto a free target therefore first drops rows at that target, which can only be stale, instead of failing on the unique key. The listing does not stat every row; such a row opens its folder, which shows the truth.

A row's "Open folder" link opens the folder that holds a file, or the folder itself for a folder entry. The empty state is its own sentence ("Nothing here yet …"), never the folder view's "This folder is empty" (#127).

Cloud sources: the item carries `source` (always `home` today). #149–#151 add each provider's recent files to the same list where the provider offers them, live from the provider, not stored in `recent`.

## 2026-10-15: the preview overlay (#142)

Question: how is a file opened for preview instead of downloaded, which types get which viewer, how is a PDF shown, what does "sanitising renderer" mean for Markdown, and how much text is fetched?

Opening. A plain click on a file's name, Enter on its row, or a double click opens the preview. The name stays a link to the download, so "open in new tab" and "save link as" still download, and the row menu, the selection bar and the preview's own "Download" button download too. The preview steps through the files of the open folder in list order: ←/→ and the Previous/Next buttons, with no wrap at the ends. Esc and Close put the focus on the row of the file shown last, not the one that was opened, so the list follows what the member looked at. Recent and the trash do not preview yet; their rows open the folder.

Types. The SPA chooses the viewer from the listed MIME type (`web/src/preview.ts`). PNG, JPEG, GIF, WebP and AVIF are images. `video/*` and `audio/*` play in the browser's own player with `preload="metadata"`. `application/pdf` is a PDF, `text/markdown` is Markdown, and any other `text/*`, JSON or XML is plain text. Plain text sits in a text node, so HTML or XML source is shown and never parsed. SVG (it can carry script), HEIC (no browser decodes it) and everything else show "can't be shown here" with Download as the forward action. A type the browser cannot decode after all (an MKV, say) shows the same failure message. The extension table gains the common text, audio and video extensions and `xml`/`xhtml`/`htm`, so these are typed correctly and HTML/XML stay attachments. AVIF joins the inline allowlist, since it is a raster format like WebP. The server's allowlist (`routes/sources.ts`) is unchanged otherwise and stays the guard; the SPA's choice is only presentation.

PDF. The browser's viewer is not used, because Chromium blocks a PDF served with `CSP: sandbox`, and phones do not show PDFs inline. pdf.js (`pdfjs-dist`, Apache-2.0) draws one page at a time on a canvas, with Previous/Next page buttons. Its worker is a file from the app's own origin, so the CSP stays `script-src 'self'`. It is loaded only when a PDF is opened and fetches the file with Range requests. One page at a time keeps memory flat on a long document. A text layer (selecting text) is not in v1 (superseded by the #143 entry: it is).

Markdown. markdown-it (MIT, CommonMark) parses with `html: false`, so raw HTML is text to it. `web/src/markdown.ts` builds Vue nodes from its tokens itself: an allowlist of elements (paragraphs, headings, lists, quotes, code, tables, emphasis), no HTML string and no `v-html`. Links are kept only for `http(s):` and `mailto:` and open in a new tab with `rel="noopener noreferrer nofollow"`. A relative link has nothing to point at inside the preview, so it is text. An image is never an `<img>`, because a remote image would be fetched as soon as the file is opened. It shows its alt text ("Image: …"), linked to its URL if that is http(s), and only a click loads it, in a new tab.

Text cap. Text and Markdown fetch at most 512 KiB, with a Range request, so the server streams only that much and the browser holds only that much. A longer file shows its start with a note and the Download button. 512 KiB covers any hand-written note and stays fast to render on a phone. An empty file is fetched without a Range, because an empty file has no satisfiable range.

## 2026-10-15: the PDF preview under `CSP: sandbox` in Chromium and Firefox (#143)

Question: does the PDF preview still work in the browsers members use, now that an inline PDF is served with `Content-Security-Policy: sandbox`, and how is "page 1 shows visible text" checked?

Delivery does not change. The browser's own viewer never opens the PDF: pdf.js in the SPA fetches the bytes from the content route (still inline, still `sandbox; default-src 'none'`) and draws them on a canvas, so the untrusted document never becomes a document of the app origin or of any frame, and the sandbox cannot get in its way. Playwright now also runs a `desktop-firefox` project, limited to `e2e/pdf-preview.spec.ts`, because the PDF path is the part that depends on the engine; the rest of the suite stays on the two Chromium projects. The check opens a two-page PDF and asserts page 1's text is in the overlay, that the canvas has ink under that text, that page 2 shows its own text after "Next page", and that no frame, embed or document navigation to the PDF exists.

## 2026-10-15: thumbnails, the gallery view and its lightbox (#144)

Question: which sizes and format, which tool makes which thumbnail and how are file names kept from becoming options, where does the cache live and how is it bounded and invalidated, what are the limits, and what do the gallery and the lightbox do?

Route and sizes. `GET /api/v1/sources/:source/thumbnail?path=…&size=128|256|512` answers a WebP whose longer side is `size` pixels (never enlarged beyond the original), with `CSP: sandbox`. Three fixed sizes keep the cache small and the URLs few: the list uses 128 for its 28 px square, the gallery 256 for its tiles. The SPA adds the file's modified time as `v`, so the answer may be cached privately for a day and a changed file gets a new URL. A type without a thumbnail is `NO_THUMBNAIL` (404); a file that cannot be decoded, or a generator that hits its time limit, is `THUMBNAIL_FAILED` (422). A tool that is missing from the `PATH` is a broken installation and answers `INTERNAL` (500, logged), not a per-file error. The route is part of the `StorageBackend` interface as `thumbnail?` (spec §3.2), so the cloud backends (#149–#151) proxy their provider's thumbnail through the same route.

Generators. Images (PNG, JPEG, GIF, WebP, AVIF; the first frame of an animation) are decoded by `sharp` in the process, with EXIF rotation and libvips' shrink-on-load, so no process is started and no file name is ever an argument. SVG has no thumbnail (it can carry script and reference other resources) and HEIC has none either (no browser shows it in the preview). A video frame comes from ffmpeg: `-protocol_whitelist file`, the demuxer fixed by the extension (`mov`, `matroska`, `ogg`), so the content of a file can never select HLS, concat or an image pattern and make ffmpeg open other files, and the input given as `file:<absolute path>`. Its `thumbnail` filter picks the most typical of the first 24 frames, so a fade-in does not give a black tile. A PDF's first page comes from `pdftoppm` (poppler-utils), with the path after `--`. pdf.js in Node was not used: it needs the whole document in memory, which the no-buffering rule forbids, and it would need a canvas binding. Both tools get only the normalised absolute path that `resolveInRoot` produced, as an element of an argument array, with `shell: false`. Their output is a small PNG on stdout, already scaled by the tool, which `sharp` turns into the WebP. Every generator has the time limit `FILES_THUMB_TIMEOUT_MS` (default 30 s; a process is killed with SIGKILL, `sharp` has its own timeout in whole seconds), and at most `THUMB_CONCURRENCY` (2) run at once across all members, so a folder full of videos cannot starve other requests on small hardware. Concurrent requests for the same file version and size share one generator run.

Cache. The files live in `<DATA_DIR>/thumbs/<id>.webp` (`thumbsDir` in `paths.ts`), beside the homes, not in them: no user path can reach them and they do not count towards a member's quota. One `thumbnails` row per file (migration 006) records member, path, size, the source file's ETag, bytes and a logical last-use clock. A row whose ETag no longer matches the file is regenerated, so a change made outside the app is never served stale. After each generation the least recently used thumbnails are removed until the total is under `FILES_THUMB_CACHE_BYTES` (default 512 MiB); the one just made is never chosen. A write, move, rename, copy target, restore, upload placement or delete in the app removes the thumbnails of the paths it touched and of everything beneath them, right after the operation. This is not in the operation's transaction: a crash in between only leaves a row whose ETag check or eviction removes it later, and the startup sweep deletes files without a row (and temp files) and rows without a file. The table is not in `PATH_TABLES`, because a thumbnail must disappear with its file, not follow it.

Gallery. The folder view has a "List / Gallery" toggle (a group of two buttons with `aria-pressed`), remembered in `localStorage` on this device. The gallery shows every entry of the folder as a tile: images, videos and PDFs with their thumbnail, folders and other files with their line icon, so the folder stays browsable. A folder tile opens the folder; a file tile opens the #142 preview overlay as the lightbox, stepping through the folder's files in list order with ←/→, as from the list. A thumbnail that fails to load falls back to the icon. The tiles are buttons in a list, reached with Tab; selection, the row menu and drag & drop stay in the list view, because the gallery is for looking through photos and the list already covers file management on every device. The list rows show the small thumbnail in place of the file icon.

## 2026-10-15: name search over a local index and live provider search (#145)

Question: what does the index hold and how does it stay true, how is a query matched, how are local and provider results merged and a failing provider reported, how is the index rebuilt, and what does the UI do with a result?

Index. One `name_index` row per file and folder of a member's home (migration 007): path, the name in NFC lower case, type, size and modified time. Folders are searchable too, because people look for "Taxes 2026" as often as for a file in it. Every write that places an item writes its row inside the write's transaction: `PUT content` (in the transaction that already records Recent, right after the rename), tus placement, `mkdir`, copy, move, rename and restore. A copied or restored folder brings the rows of its whole tree (walked before the transaction, in the staging or trash area), and the folders a folder upload or a restore creates on the way get rows if they have none. Moves and deletes, including a replaced target, reach the rows through `PATH_TABLES`, and the moved item's own row is written again because its name may have changed. Size and modified come from the index, not from a `stat` per result, so a search never touches the disk and stays fast on small hardware; they are what the app last wrote, like Recent. A row the app did not write (a change made on disk outside the app) is fixed only by the rebuild.

Matching. A query is 1–200 characters after trimming, matched anywhere in the name, ignoring case (`toLowerCase` after NFC on both sides), with SQLite `instr()`. There is no `LIKE` and no FTS, so `%`, `_`, quotes and brackets are plain characters and cannot widen a query. Exact names come first, then names that start with the query, then shorter names. No FTS5 index: substring search is what people expect from a name box ("2026" inside "Taxes-2026.pdf"), FTS tokenises words instead, and a scan of one member's rows is fast enough for a home of tens of thousands of items. Full-text content search stays deferred (#131).

Merge. `GET /api/v1/search?q=` asks the home and every connection of the caller (`conn:<id>`) whose backend implements `search?(query, limit)` at the same time, and answers `{ groups: [{ source, items, more, error? }] }`, home first, in connection order. Each source gives at most 50 items; `more` says there were further ones, so the UI can ask for a longer query instead of paging. A source that fails becomes a group with no items and `error.code`: the code of an `AppError` it threw, otherwise the new `SEARCH_FAILED` (502), logged with the source. The request itself still answers 200 with the other groups, so one broken provider never hides local results. Connections come from `deps.connections`, which is empty until #148 adds connection rows; shares are not searched (#146 decides whether a share's files belong in the searcher's results).

Rebuild. `node server/dist/reindex.js [userId…]` (`pnpm --filter @files/server reindex` in development) walks the homes like a listing does (no symlinks, no temp files, no internal area, no unaddressable names) and replaces each member's rows in one transaction. Started as root by `docker exec`, it drops to uid 1000 first, like the server. There is no rebuild at startup: nothing is deployed yet, so no home predates the index, and walking every home on each start would slow the boot of a large shard. A write that lands while a home is being walked may be missed, so the command is for an idle or stopped app.

UI. The search field sits in the header, available from every view. It is a combobox: the results are one listbox grouped by source, the arrow keys move the active result (`aria-activedescendant`, the focus stays in the field), Enter opens the active result or the first one, Esc closes the results and a second Esc clears the field. A file opens the folder that holds it with `?select=<path>`, which selects the file and focuses its row once the folder is listed; a folder opens itself, as in Recent. Typing waits 200 ms before asking, and only the newest answer is shown. No results is its own sentence ("Nothing found with “…” in its name"), and a source that failed is named under the results with its error.

## 2026-10-15: internal shares, "Shared with me", the share dialog and the details drawer (#146)

Question: what does a share point at and who may create one, how is a shared path confined, what happens to a share when its item moves or goes, who counts as a member, what may a grantee do in the UI, and are shares searched?

Rows. One `shares` row per item and grantee (migration 008): owner, source, path, type, grantee, access (`read`/`edit`), creation time and `orphaned_at`. A partial unique index keeps one live share per item and grantee; sharing the same item with the same member again changes the access of that row instead of adding one. The id is 16 random bytes in hex. `POST /api/v1/shares` takes `{ source, path, grantee, access }` and nothing else (unknown fields are `VALIDATION`), so a share is always the caller's own: the owner is the session user, `home` is the caller's own home, and the item must exist there (`NOT_FOUND`), which is how "on behalf of another member" (#114) is closed. A `share:<id>` source is `FORBIDDEN` as a share's source: a grantee cannot pass on access the owner can no longer see or revoke. The home root is not shareable (`PATH_INVALID`); members share folders and files in it. Sharing with oneself is `VALIDATION`, with an unknown member `NOT_FOUND`.

Access. `resolveSource` reads the row on every request, with the grantee in the lookup, so another member's share, an unknown id and a revoked one are all `SOURCE_NOT_FOUND` (404), and a changed access level applies to the next request. A grantee reaches the item through `ShareBackend` (`server/src/storage/shares.ts`): `/` is the shared item itself, every path is normalised (no `..`) and then put beneath the owner's path, and entries come back with share-relative paths, so the owner's folders above the item are never revealed. The shared item itself can be read and, for a file under `edit`, overwritten, but not renamed, moved, copied or trashed (`FORBIDDEN`): that would change the owner's tree outside what was shared. The routes keep deciding `read` against `edit` as for every source (`FORBIDDEN` for a change under `read`). Changes by the grantee happen in the owner's home with the owner's rows (trash, Recent, name index, thumbnails), because it is the owner's data. A share of a cloud file reaches the owner's own connection on the server (`deps.connections(owner)`); a connection that is gone answers `SHARE_ORPHANED`. No connection exists yet (#148).

Moves and deletes. `shares` joins `PATH_TABLES` with two new optional fields: `sourceColumn` limits the cascade to rows of the home, and `orphanColumn` makes a delete set `orphaned_at` instead of removing the row. A move of the item or a folder above it rewrites the path in the move's transaction, also when the grantee moves things inside an edit share. A delete, a delete of a folder above it and a "replace" that trashes it orphan the share in the same transaction; it then answers `SHARE_ORPHANED` (410) and never follows a new item that takes the old name (#95). An orphaned row no longer moves. Restoring the item from the trash does not revive its shares: the owner shares it again if that is still wanted, since the trash is not a promise that sharing continues. "Shared with me" lists an orphaned share as "No longer available" with "Remove from list"; the owner revokes and the grantee leaves a share with the same `DELETE /api/v1/shares/:id`, anyone else gets `NOT_FOUND`.

Members. "Members known to the shard" are the people who have signed in to Files at least once (`users` rows), because shard_core offers no member directory to Files yet. `GET /api/v1/members` lists everyone else by name with id and display name only, no e-mail. The picker filters that list in the browser by a case-insensitive substring of the name; a shard has a handful of members, so no server-side search is needed.

UI. The row menu offers "Share" in the member's own home and "Details" everywhere. The share dialog (`<AppDialog>`) is a combobox member picker (arrow keys, Enter picks, Esc closes only the open list), the access level as two radios ("Can view" is the default, because it cannot lose data), "Share", and "Who has access" with "Remove access" per member; removing puts the focus back into the member field so it never drops out of the dialog. The details drawer is an `<AppDialog drawer>` at the right edge (a bottom sheet on a phone) with type, size, modified, location and who has access, plus "Share …" in the home. "Shared with me" is a sidebar entry and its own view: name, owner, access, date; a folder opens as `/share:<id>`, a file downloads. The SPA URL keeps the `:` of the source readable. A listing now carries the caller's `access`; with `read` the folder view offers only download and details (no rename, move, copy, trash, paste, drag & drop or change keys). Upload into a share is not offered, not even with `edit`: tus stages and places the bytes in the uploader's own home, and placing them into another member's home needs its own placement and quota decision (whose quota pays). That comes with the transfers work (#152); `PUT content` already accepts writes into an edit share for API clients. Moving or copying between a share and the home is #152 as well, so the clipboard pastes only into the source it was taken from.

Search. Shares are not searched. The owner's index rows are the owner's; searching them for a grantee would need a per-share prefix filter on another member's rows, and nothing in the issue asks for it.

## 2026-10-15: public links (#147)

Question: how are links addressed and stored, how is a password checked and remembered, what counts as a download, what does an expiry accept, how does the visitor's page work, and what does the owner manage?

Routes. Everything a visitor reaches is one public route, `GET|POST /s/:token/*` (`server/src/routes/links.ts`), with `info`, `unlock`, `list` and `content` after the token; it carries `config: { public: true }` because visitors have no session, and the token, password, expiry and limit are checked in the handler on every request. `HEAD` is not derived from it, because Fastify would run the handler, which counts. The page itself is `/s/<token>` without a trailing part, which this route does not match, so the SPA fallback serves `index.html` under the app's CSP and the SPA renders `PublicLinkView` outside the signed-in shell, without `/api/v1/me`. The owner's side is `/api/v1/links` (create, list per item, `PATCH`, `DELETE`) with session and CSRF like every route. A link is always to the caller's own item: `share:` sources are `FORBIDDEN`, as for internal shares, and the home root is `PATH_INVALID`. An item may have several links (one per recipient, told apart by the label, which only the owner sees).

Rows. One `public_links` row per link (migration 009): owner, source, path, type, label, the argon2id hash of the password (`@node-rs/argon2`, as the spec names for app passwords), expiry, `max_downloads` (NULL = no limit, 0 = none), `downloads` and `orphaned_at`. The token (16 random bytes, base64url, 22 characters) is stored as it is, because the owner copies the address again later; it is a capability like a share id, and a database leak exposes the files anyway. It joins `PATH_TABLES` with `sourceColumn` and `orphanColumn`, so a link follows moves and a delete orphans it; an orphaned link, and one to a connection the owner unlinked, answers `SHARE_ORPHANED` (410), reached through the same `ownerSource` as internal shares, so it never falls back to the home (#95). Content goes through `ShareBackend`, so `/` is the linked item and nothing above it can be named. A revoked or unknown token is `NOT_FOUND`.

Password. Wrong passwords are counted in memory (the app is one process) per link and per address (`req.ip`, one trusted proxy hop) in a 15-minute window that starts with the first failure: the 6th attempt on a link within the window, or the 21st from one address across links, answers `TOO_MANY_ATTEMPTS` (429) with `Retry-After` before the hash is checked, a correct password included. Counting per link means a stranger can lock a link for 15 minutes; that is the price of stopping a guesser who rotates addresses, and the owner can hand out a second link. A correct password sets a signed (session secret) cookie `__Secure-fs_link` (`fs_link` on http loopback), `HttpOnly`, `SameSite=Strict`, `Path=/s/<token>/`, for one hour. Its value names the link, the end time and a digest of the current password hash, so it unlocks only that link and dies when the password is changed or removed. `__Host-` is not possible with a path. Unlock checks the `Origin` like CSRF does, so another site cannot make a visitor's browser guess.

Downloads. Every answer of `content` that serves bytes counts, whatever the query (`inline`, a Range, anything): a preview is a download (#104). The file is opened first and then counted in one `UPDATE … WHERE downloads < max_downloads`, so a missing file or an unsatisfiable range costs nothing, and two requests can never both take the last download. A video played in a new tab makes several Range requests and uses several downloads; that is what "previews count" means. Listing a folder and `info` serve no file bytes and do not count. A link to a folder counts each file. Changing the limit keeps the count. Content is always `CSP: sandbox` and `nosniff`; it is inline only with `?inline` and for the same allowlist as the app (`server/src/http/content.ts`, now shared by both routes), so HTML, SVG and XML are always attachments.

Expiry. The owner sends an ISO date-time with offset in the future, or `null` for none. Anything else, a past time, an unparsable string, a number or a date-time without offset, is `INVALID_EXPIRY` (400), on creation and on change, and never means "no expiry". A stored expiry that cannot be read counts as expired. An expired link answers `LINK_EXPIRED` (410) everywhere.

Visitor's page. It shows the name as text (Vue interpolation, no `v-html`) and nothing but name and type until the password is entered. A file has "Download" (a plain link to `content`) and, for types the server shows inline (images, video, audio, plain text; not PDF, which Chromium's viewer refuses under `CSP: sandbox`), "Open preview" in a new tab. A folder lists its entries; subfolders open in the page with `?path=`, files download one by one (no ZIP of a link in v1). A refused download that the browser navigated to (`Sec-Fetch-Mode: navigate`) is answered with a redirect to `/s/<token>?error=<code>`, and the page shows the message in the visitor's language (`resolveLocale`: stored choice, browser, Deutsch Du), instead of the browser showing a JSON body. Any other client gets the JSON error. Logs replace the token in `/s/<token>/…` with `<token>`.

Management. "Public links" in the share dialog lists the item's links with label, password yes/no, expiry, downloads and the address, with "Copy" (clipboard, or the address is selected when the clipboard is not available), "Edit" and "Revoke". One form below the list creates or edits a link: label, expiry (`datetime-local`, sent as UTC ISO; a value the browser cannot read is sent as typed and the server answers `INVALID_EXPIRY`), limit (empty = none) and password (empty = none, or keep the current one when editing, with "Remove the password"). Esc in the form closes only the form. Revoking does not ask first, like removing a member's access. Custom branding of the page is deferred (#131).

## 2026-10-15: cloud connections, the OAuthClient and the fake provider (#148)

Question: which providers exist before their backends do, where do tokens, `state` and the PKCE verifier live, how is the redirect URI built, what do refresh, backoff and "needs re-auth" mean, what does unlink do to shares, and how are E2E and live tests run without test code in the production bundle?

Providers. A provider is a definition with fixed endpoints, client credentials, scopes, a PKCE flag, `account()` and `backend()` (`server/src/cloud/oauth.ts`), passed to `buildApp` as `providers`. Production offers none yet (`PROVIDERS` in `app.ts` is empty): a connection to Google Drive, Dropbox or Graph without its backend could not list a single file, so each provider arrives with its backend in #149–#151, with its client credentials as optional config. Until then "Cloud accounts" says that no provider is set up on this shard. No endpoint ever comes from a request or from a member, so the server only calls fixed hosts.

Rows and secrets. One `connections` row per member and provider account (migration 010, unique on member, provider and the provider's account id), so connecting the same account again refreshes that row instead of adding a second one. The refresh token is AES-256-GCM ciphertext under the HKDF key from `FILES_ENCRYPTION_KEY` (`server/src/cloud/secretBox.ts`), `v1.<iv>.<tag>.<ct>`, with the row's id as additional authenticated data, so a ciphertext copied into another row does not open. A changed byte, another key or a moved value fails authentication and the request answers `INTERNAL` (500, logged) before anything is sent to the provider; it never turns into a garbage token or a silent "needs re-auth". Access tokens live in memory only, in one `OAuthClient` per connection and process (`CloudConnections` in `server/src/cloud/connections.ts`), since they last an hour and a restart only costs one refresh.

Consent. `POST /api/v1/connections/authorize` (session and CSRF, like every route) creates a `connect_attempts` row with a 32-byte `state`, the PKCE verifier (S256, only where the provider supports PKCE), the member and the hash of the session, for 10 minutes, and answers the provider's consent URL; the SPA navigates there. The provider sends the browser to `GET /api/v1/connections/callback`, a normal session route (the cookie is `SameSite=Lax`, which a top-level navigation carries). A callback without `state`, with a state that this session did not start, with a spent state or with `error=` exchanges nothing and stores nothing; it redirects to `/connections?error=CONNECT_FAILED`, and the reason goes to the log. The redirect URI is `<FILES_PUBLIC_URL>/api/v1/connections/callback`, built once at startup, never from `Host` or `X-Forwarded-Host` (#106). The request log already keeps only the path; the callback logs a reason and the error, never the query, and token errors carry only the HTTP status, so neither code, state nor token reaches a log line. A finished consent opens the new connection (`/conn:<id>`).

Signing in again. "Sign in again" runs the same flow with the connection's id in the attempt. The tokens go into that row only if the provider reports the same account; another account is `CONNECT_ACCOUNT_MISMATCH` and the row stays as it was, since shares into the connection must not suddenly point into someone else's files.

Refresh and backoff. The access token is renewed 60 s before it expires and on a 401; concurrent requests share one refresh (single flight per connection), and only a request that saw the current token fail drops it. A refresh token the provider rotates is written to the row before the new access token is handed out, so no request can run with tokens the database does not have. A refused refresh (400/401 from the token endpoint) or a 401 right after a fresh token sets the status `reauth` and answers `CONNECTION_REAUTH` (409, not 401, which would send the SPA to the shard login). 429, 5xx and network failures are retried up to 3 times: after `Retry-After` (seconds or an HTTP date) when the provider sends it, else after 0.5, 1 and 2 s, plus up to 0.5 s of jitter either way; a `Retry-After` above 30 s is not waited for. Then the answer is `PROVIDER_UNAVAILABLE` (503). A request whose body is a stream can only be sent once (`retry: false`), and the backend handles its answer. Time and chance are injected (`Clock`), which is how the tests run the backoff on a fake clock.

Status (#41). The list shows the stored status: `ok`, `reauth`, or `unavailable` when the provider is no longer offered (only computed, so such a connection can still be unlinked). Opening "Cloud accounts" runs `POST /api/v1/connections/:id/check` per connection, which asks the provider who the account is and so updates the status. There is no background health job: nothing happens on the member's behalf while nobody looks.

Ownership. `conn:<id>` resolves only among the caller's own connections (`deps.connections(user)`), so another member's connection is `SOURCE_NOT_FOUND`, and the connection routes answer `NOT_FOUND` for it, as for an unknown id. The owner has `edit` on their own account. Shares and public links into a connection reach it on the server through the owner's connections (`ownerSource`, #146/#147).

Unlink (#58). `DELETE /api/v1/connections/:id` removes the row and, in the same transaction, orphans every share and public link of that member into `conn:<id>` (`orphanSourceRefs` in `pathRefs.ts`, which goes over the `PATH_TABLES` that carry a `sourceColumn`, orphaning or else deleting). They answer `SHARE_ORPHANED` (410) and stay orphaned when the same account is connected again, because the new connection has a new id: the member decides again what to share. Unlink is asked first in an `<AppDialog>` (`ConfirmDialog`, Cancel focused), because it ends shares, which the trash cannot bring back. Files never leave the provider, and the grant at the provider is not revoked: no provider offers a uniform revocation, so the dialog tells the member where to do it.

Fake provider and E2E. `server/test/support/fakeProvider.ts` is an OAuth server with a consent page (Allow/Deny, two accounts), PKCE, rotating refresh tokens and controls for expired tokens, revoked grants and injected 429/5xx, plus a file API with pagination, a 302 to a pre-signed content URL and chunked upload sessions; `FakeCloudBackend` is a `StorageBackend` over it. #149–#151 add each provider's own protocol subset to it. ## 2026-10-15: the Google Drive backend (#149)

Question: which part of a Google account is shown, how are paths mapped onto Drive's ids when names can repeat, what happens to Google Docs, Sheets and Slides, what does delete do, how do uploads and downloads stay streaming, how does a member upload into a connection, and how is the provider configured?

Scope. The scope is `https://www.googleapis.com/auth/drive`. `drive.file` would show only files the app created itself, and `drive.readonly` could not upload, so neither can browse a member's Drive. Only "My Drive" is shown: the root and everything below it. Shared drives (`supportsAllDrives`) and items under "Shared with me" that were never added to My Drive are left out of v1. They need a second root in the source model, and a path for an item without a parent in My Drive. Search leaves them out for the same reason. Google calls `drive` a restricted scope: a shard owner's own OAuth client in "testing" or internal mode can use it without Google's verification, and that is the expected setup for a self-hosted shard.

Paths and ids. A path is resolved one segment at a time: Drive's `name = '…'` query in the parent folder, and the export extension of a Google-native document may be part of the segment. Every resolved path → id is cached for 30 s per connection, together with every name a listing returned. The cache lives beside the connection's `OAuthClient`, because backends are built per request. A change through the app drops the paths it touched and everything below them at once. A change made elsewhere shows after at most 30 s, and a cached id whose item was trashed meanwhile is resolved once more. Drive lets one folder hold several items of the same name, and its names may contain `/`, `\` or control characters. Such items are never merged and never hidden. An item whose name is taken more than once in its folder, or whose name had to be changed to be a path segment, is listed as `name (~<fileId>).ext`. That name resolves to exactly that item, after a check that the id really is a live child of the folder and gives the same listed name. The bare name of a duplicate answers the new `AMBIGUOUS_NAME` (409, `{ name }`), never the first match. Renaming one of them through the app (the move strips the marker) ends the clash. Listing follows `nextPageToken` to the end, so duplicates are found across pages; there is no cursor to hand through.

Google-native documents. Docs, Sheets and Slides are listed with `.docx`, `.xlsx` and `.pptx`, and Drawings with `.pdf`. They have size 0, since Drive reports none. A download exports them through `files/<id>/export` to that format. An export has no ranges and no length up front, so `read` marks it `unsized`: the content route then sends no `Content-Length`, says `Accept-Ranges: none` and answers 200 to a Range request. Forms, Sites, Maps and shortcuts are listed under their own name, and a download answers the new `NOT_EXPORTABLE` (422). The member opens them at Google. Moving or renaming a native document keeps Drive's name without the added extension.

Delete. Delete sets `trashed: true` (`PATCH files/<id>`) on every item. A permanent `DELETE` is never sent, and the fake Drive records it so the test can assert that. Every path is resolved before anything is trashed, so a missing path changes nothing. If trashing fails halfway, the items already trashed are restored. "Replace" in move, copy and upload sends the item in the way to Drive's trash. The one exception is an upload that replaces a regular file: it uploads a new revision of the same file id, which Drive keeps as a revision, so nothing is lost. `revisions(path)` lists those revisions; restoring one comes with the versions issue. `quota()` reads `about.storageQuota`; the storage overview will show it.

Streaming. Downloads go to `files/<id>?alt=media` with the Range passed on. Redirects are never followed automatically: a 3xx is followed at most three times, only to Google's content hosts (`www.googleapis.com`, `*.googleusercontent.com`) and without the bearer token. A redirect anywhere else fails as `INTERNAL` before a request leaves the shard (spec §3.7). Uploads open a resumable session (`uploadType=resumable` with `X-Upload-Content-Length`) and check that the session URI is on the upload host. The body then goes in 8 MiB chunks (a multiple of 256 KiB, as Drive requires), and the next chunk waits for the 308. One chunk is all an upload holds in memory, and a 1 GB transfer in each direction is tested to stay under 96 MiB of extra heap. A body longer or shorter than the declared size cancels the session (`DELETE` on its URI) and answers `SIZE_MISMATCH`. A session needs the length up front, so a write without `size` is `VALIDATION`. Missing parent folders are created, as in the home. A failed chunk is not retried: the member retries the upload. Thumbnails are Drive's own `thumbnailLink` at the requested size, fetched by the server only from Google's content hosts and re-encoded as WebP by `sharp`. Neither that link nor any other Google URL is ever put into an answer.

Search. Drive's `name contains` matches word prefixes. Its results are narrowed to names that contain the query anywhere, ignoring case, like the home's search. Drive therefore finds a subset of what a substring search would, never more. Each result gets its path by walking its parents to the root, and anything that does not reach My Drive's root is left out.

Upload in the SPA. The folder view of a member's own connection now offers upload and desktop drops. tus places bytes only into the home (#152), so a cloud target gets one streaming `PUT content` per file (`web/src/api/directUpload.ts`), which the server passes on to Drive's resumable session. With `fail`, the SPA asks `stat` first, so the browser never sends a body that the server already refused. Pause aborts the request and resume sends the file again. Nothing is resumed across a reload. Shares still get no upload button (#146, #152).

Configuration. `FILES_GOOGLE_CLIENT_ID` and `FILES_GOOGLE_CLIENT_SECRET` are optional as a pair (one without the other stops the start). With them, "Cloud accounts" offers Google Drive. The endpoints are constants in `server/src/cloud/googleDrive.ts`, never config. The consent asks for `access_type=offline` and `prompt=consent`, so Google issues a refresh token also when the account was connected before. PKCE is S256. The account id is Drive's `permissionId` and the label is the e-mail address. The provider's redirect URI to register at Google is `<FILES_PUBLIC_URL>/api/v1/connections/callback`. The live tests now read `LIVE_GDRIVE_*` (formerly `LIVE_GOOGLE_*`).

Not in this issue: the provider's recent files in Recent (#141 named it for #149–#151; the issue's scope does not list it), restoring a revision, and moves or copies between Drive and another source (#152).

## 2026-10-15: the Dropbox backend (#150)

Question: which scopes and part of the account are used, how do case-insensitive paths behave, is the listing cursor handed to the client, what does delete do, how do uploads stay streaming, what is a folder's modified time, and how is the provider configured?

Scopes. `account_info.read files.metadata.read files.content.read files.content.write`: browsing, transfers and the account label, nothing for sharing or teams. The consent asks for `token_access_type=offline`, so Dropbox issues a refresh token; its access tokens last four hours and the `OAuthClient` renews them. Dropbox does not rotate refresh tokens, which the `OAuthClient` already handles. PKCE is S256. The account id is Dropbox's `account_id`, the label the e-mail address. The whole Dropbox of the account is shown, from its root (`""`); team spaces and shared folders appear wherever Dropbox mounts them for the account.

Case. Dropbox paths ignore case: `/a.txt` and `/A.txt` are one item, and Dropbox keeps the case it was created with. Every path comparison in `DropboxBackend` is made lowercased: a name taken in another case is taken (`FILE_EXISTS`, and "keep both" counts `B (1).txt` as taken by `b (1).txt`), a folder never moves or copies into itself in any case (`TARGET_INSIDE_SOURCE`), and a delete of `/Bin/Sub` and `/bin/sub/b.txt` deletes `/Bin/Sub` once. A rename that only changes case (`a.txt` → `A.txt`) is the item itself in the way, never a collision: it moves to a temporary `.files-rename-<hex>` name and from there to the new one, and goes back if the second step fails, because Dropbox has refused case-only moves as a conflict. Copying an item onto itself in another case is the same item: "fail" asks, "replace" leaves it as it is (it must never delete the source), "keep both" duplicates. Entries carry Dropbox's name for the last segment and the folder path as the client asked for it.

Listing. Dropbox's `list_folder` pages are handed to the client one per request (`next`), because the SPA, the ZIP stream and public links already follow `next`, and a big Dropbox folder then starts showing at once. `next` is Dropbox's cursor bound to the lowercased folder it lists; a cursor for another folder, or one that cannot be read, is `VALIDATION` before anything is sent to Dropbox, so a cursor cannot continue a listing the path does not name (a share or link is confined by its path). Inside the backend (free names) the listing is followed to the end. The page size is the route's `limit` (default 500, at most 2000, Dropbox's range).

Delete. `delete_v2` puts items into Dropbox's deleted files, from which the member restores them at Dropbox; `permanently_delete` is never sent, and the fake counts it so the test can assert that. "Replace" in move, copy and upload does the same with the item in the way, except that an upload replacing a file commits with `overwrite`, which Dropbox keeps as a revision of the same file. Every path is looked up before anything is deleted, so a missing one changes nothing. Dropbox has no transaction and folders cannot be restored through the API, so a delete that fails halfway leaves the items before it in Dropbox's deleted files; the member sees the error and can restore them there.

Streaming. Downloads are one `files/download` with the Range passed on (plus `get_metadata` first when the range depends on the size); redirects are never followed. Uploads are an upload session: `start` with the first 8 MiB chunk, `append_v2` per chunk, `finish` with the rest and the commit (`add`; `overwrite` for replace; `update` with the revision for `If-Match`, so a changed file is `PRECONDITION_FAILED` at Dropbox itself). One chunk is all an upload holds in memory, and a 1 GB transfer in each direction is tested to stay under 96 MiB of extra heap. Dropbox needs no length up front, so a write without `size` works; a body longer or shorter than declared, or above the upload limit, never reaches `finish`, so nothing is created and Dropbox drops the open session itself. Chunks are buffers, so a chunk answered with 429 or 5xx is sent again by the `OAuthClient`. Arguments of content endpoints go in `Dropbox-API-Arg`, which must be ASCII: every other character is sent as a JSON `\u` escape. Thumbnails are Dropbox's `get_thumbnail_v2` at the smallest of its sizes that covers the asked one, re-encoded as WebP by `sharp`; a type Dropbox has no thumbnail for is `NO_THUMBNAIL`. The ETag of a file is its revision.

Folder times. Dropbox reports no modified time for a folder. Rather than make one up (the epoch would read "1 Jan 1970"), `Entry.modified` is now optional: a Dropbox folder has none, the folder view leaves its date cell empty, the details drawer leaves out the line, and a ZIP gets the earliest DOS date for it.

Search. Dropbox's `search_v2` (file names only, active files) matches words; its results are narrowed to names that contain the query anywhere, ignoring case, like the home's and Drive's search. Paths are Dropbox's `path_display`, whose folder part may differ in case from the stored one; Dropbox finds the item by it all the same.

Configuration. `FILES_DROPBOX_CLIENT_ID` (the app key) and `FILES_DROPBOX_CLIENT_SECRET` (the app secret) are optional as a pair; with them "Cloud accounts" offers Dropbox. The endpoints are constants in `server/src/cloud/dropbox.ts`. The redirect URI to register in the Dropbox app console is `<FILES_PUBLIC_URL>/api/v1/connections/callback`. The live tests read `LIVE_DROPBOX_*`.

Not in this issue: webhooks and delta sync (#131), Dropbox's recent files in Recent, restoring a revision, and moves or copies between Dropbox and another source (#152).

## 2026-10-15: the Microsoft Graph backend, OneDrive and SharePoint (#151)

Question: is OneDrive one provider with SharePoint or two, what does a connection show, how does the member pick a SharePoint library after the consent and can it change, which scopes and tenant are used, how are listings, downloads, uploads and copies done without following a URL Graph did not issue for its own hosts, and what does delete do?

Two providers, one app. "Cloud accounts" offers OneDrive and SharePoint as two buttons, both over the same Azure app registration (`FILES_GRAPH_CLIENT_ID`/`_SECRET`). A OneDrive connection is one click: consent, and it shows the account's own drive (`/me/drive`), personal or work. A SharePoint connection shows exactly one document library (`/drives/{id}`): after the consent the callback sends the member to `/connections?pick=<id>`, where the library picker (an `<AppDialog>`) lists the sites the account reaches (`/sites?search=`, all of them for an empty search; Graph's first page, so a long list is narrowed by searching) and a chosen site's document libraries. Until a library is picked, the connection's status is `library` ("No library chosen yet"), its row offers "Choose library", and `conn:<id>` is `SOURCE_NOT_FOUND`: never a fallback to the account's OneDrive. One library per connection keeps a source one tree, like every other source, so shares, links, search and the ZIP stream need nothing new. Several libraries of one account are several connections: each consent of SharePoint adds one (or reuses the account's connection still waiting for a library), and the same library twice for one account is `LIBRARY_ALREADY_CONNECTED` (409). A picked library never changes (`VALIDATION`), because shares and links into the connection must not start pointing at other files; the member connects another library instead. The connection row gets `drive` (the library id, `''` for the account's own files) and `drive_label` ("Site / Library", shown under the account) in migration 011, and the uniqueness moves from (member, provider, account) to (member, provider, account, drive). "Sign in again" checks the account against the row itself and keeps its library. Teams-specific features are out, as the issue says. There is no field to paste a refresh token anywhere (#87).

Scopes and tenant. OneDrive asks for `offline_access User.Read Files.ReadWrite` (the account's own files); SharePoint for `offline_access User.Read Files.ReadWrite.All Sites.Read.All` (every library the member can reach, and the site search). Neither needs an administrator's consent in a default tenant. PKCE is S256; Microsoft rotates refresh tokens, which the `OAuthClient` already stores first. The account id is Graph's user `id`, the label `mail`, else `userPrincipalName`. The sign-in URL is `https://login.microsoftonline.com/<tenant>/oauth2/v2.0/…` with `FILES_GRAPH_TENANT`, `common` by default (work and personal accounts); a single-tenant registration sets its tenant id or domain. National clouds (Graph hosts other than `graph.microsoft.com`) are out of v1.

Fixed hosts. Every API request goes to `https://graph.microsoft.com/v1.0`. Site and library ids from the member are checked against `GraphId` (letters, digits, `!.,_-`) before they become a path segment, and a library is taken only if Graph lists it among the site's document libraries. A listing follows `@odata.nextLink` to the end, but only while the link stays below the Graph API; any other link fails as `INTERNAL` before it is requested. Downloads (`/content`), thumbnails, upload sessions and copy monitors are pre-signed URLs; they are called only on Microsoft's content hosts (`*.sharepoint.com`, `*.1drv.com`, `*.livefilestore.com`, `*.onedrive.com`, and since #202 `*.microsoftpersonalcontent.com` and `*-mediap.svc.ms`) over https and never with the bearer token, and anything else fails before a request leaves the shard.

Transfers. A download looks the item up (size, ETag), asks `/items/{id}/content`, follows its 302 on the server with the Range passed on, and streams the answer; an unsatisfiable range is answered from the known size. An upload opens `createUploadSession` with the conflict behaviour `fail` (the app asks first), `replace` (a new version of the same file, also used for If-Match, which Graph checks itself with `If-Match` on the session) or `fail` at a free name for "keep both"; the body goes up in 10 MiB chunks (a multiple of 320 KiB, as Graph requires) with `Content-Range`, one chunk in memory, and a 1 GB transfer in each direction is tested to stay under 96 MiB of extra heap. A session needs the length up front, so a write without `size` is `VALIDATION`; a body longer or shorter than declared cancels the session (`DELETE`), so nothing is created. An empty file has no range to send and goes up as one empty `PUT …:/content`. Missing parent folders are created, as in the home. A failed chunk is not retried: the member retries the upload. Thumbnails are Graph's `medium` (176 px) or `large` (800 px), the smallest that covers the asked size, re-encoded as WebP; a file without one is `NO_THUMBNAIL`.

Copy, move, delete. A copy is Graph's asynchronous copy: it answers 202 with a monitor URL, which the server polls (after 0.5, 1 and 2 s, then every 2 s, for at most ten minutes, then `PROVIDER_UNAVAILABLE`) until it reports `completed` or redirects to the new item; `failed` with `nameAlreadyExists` is `FILE_EXISTS`. Moves and renames are one `PATCH` of name and parent. OneDrive and SharePoint names ignore case: collisions and "keep both" compare lowercased, and a rename that only changes the case is the item itself, which Graph renames as it is. Delete is `DELETE`, which puts the item into the drive's recycle bin; `permanentDelete` is never sent, and the fake counts it. "Replace" in move, copy and folder-for-file uploads sends the item in the way to the recycle bin the same way. Every path is looked up before anything is deleted; Graph has no transaction, so a delete that fails halfway leaves the items before it in the recycle bin.

Search and the rest. Graph's drive search (`root/search(q=…)`) matches words and content; results are narrowed to names that contain the query, ignoring case, like the other sources, and get their path by walking their parents to the drive's root (a search result carries no reliable path); an item that does not reach the root is left out. `quota()` reads the drive's `quota`, `revisions()` its versions (restoring one comes with versions).

Not in this issue: Teams-specific features, national clouds, changing a connection's library, OneDrive's or SharePoint's recent files in Recent, restoring a version, and moves or copies between Graph and another source (#152).

## 2026-10-15: transfer jobs between sources (#152)

Question: what does a job contain and how is it addressed, what does "verified" mean when the providers' hashes differ, when does a move delete its source, how do collisions and cancel work, and what happens on a restart?

Model. `POST /api/v1/transfers` takes `{ mode, from, to, dir, items: [{ path, onCollision }] }`: items of one source into the folder `dir` of another source. Within one source the direct `move`/`copy` routes stay (`from === to` is `VALIDATION`); turning those into jobs too (spec §3.4) is left for later. Both sources are resolved with the caller's rights before a row exists (`to` needs `edit`, a move also needs `edit` on `from`), and again for every item from the job owner's rows (`sourceFor` in `resolveSource.ts`), so an unlinked connection or revoked share fails the remaining items instead of reaching anything. A job row plus one row per item (migration 012); a folder item lists its folder when it runs and adds the children as items in the transaction that marks it done. Every lookup is by id and owner, so another member's job is `NOT_FOUND`. `GET /api/v1/transfers` lists the caller's newest 50 jobs, `POST …/:id/cancel` cancels, `POST …/clear` removes the caller's finished jobs, `GET …/events` is the SSE stream.

Workers. In-process, at most two items at a time over all jobs (`TRANSFER_CONCURRENCY`), oldest job first: enough to overlap round trips, few enough for the providers' rate limits. No upload size limit applies (a transfer is not an upload); the home's quota still does, through the backend's `write`.

Verification (#99). A file item streams `read` into `write` through a meter that counts and hashes (SHA-256) the bytes. It is done only if the bytes read match the size the source announced (`SIZE_MISMATCH` otherwise; a Google-native export has no announced size), the target's `stat` shows a file of exactly that size, and, where a side offers `StorageBackend.digest` (SHA-256 of the stored bytes), that digest equals the hash of what was sent (`VERIFY_FAILED` otherwise, a new error code). Only the home offers `digest` today: Drive gives MD5, Dropbox its block `content_hash`, Graph `quickXorHash` or SHA-256 depending on the drive, so comparing them would need a second hash of the stream per provider; that is left until a provider-specific check is worth it. A job reports `completed` only if every item is done, otherwise `completed_with_errors` with the failed items and their codes.

Moves. Nothing is deleted while the job runs. When no item is pending or in flight, the source of every done item is deleted (to the source's trash): a folder as a whole where everything beneath it is done, otherwise the done files one by one, so a failed item and the folders above it always keep their source. A source that cannot be deleted turns its item failed. A cancelled move does the same for the items done before the cancel.

Collisions (#136). The SPA asks the collision question before the job starts, for each picked name that the open folder's listing already shows (with "apply to all"); skipped items are left out of the request, the rest carry `fail`, `replace` or `keep-both`. A folder under `keep-both` gets a free `name (n)`, under `replace` the old one goes to the target's trash first. The folder's path is stored before it is created, and children are written with `replace`, because whatever lies in a folder the job created came from the job (an earlier attempt).

Cancel and restart. Cancel marks the job `cancelled` and its pending items at once, and aborts the items in flight by destroying the stream the target reads, so the target's write removes what it had staged; an item whose write had already finished is verified and counted as done. On shutdown the items in flight are aborted the same way but stay `active`; at start-up (after the temp-file sweep) `active` items become `pending` again and running jobs continue. A file's placed path is stored right after its write, so a resumed item replaces exactly that copy. A crash in the short window between a write and that update can leave a duplicate (`keep-both`) or report `FILE_EXISTS` (`fail`), never a false success.

Progress. `GET /api/v1/transfers/events` (`text/event-stream`) first sends the caller's jobs, then a `job` event with the whole job on every change and at most every 250 ms while bytes flow. Only the owner's listeners get a job's events. The SPA opens one `EventSource` after sign-in; the browser reconnects by itself and the server then sends the jobs again. The transfer panel (above the folder, below the upload panel) shows one row per job with "n of m" and the bytes, a progress line over the settled items, "Cancel" while it runs, the failed items with their reasons once it has ended, and "Clear finished". A folder relists when a job into it (or a move out of its source) ends.

Paste. The clipboard already holds `{source, entries}`. Pasting into the same source keeps the direct requests; pasting into another source starts a job (#115).

## 2026-10-15: migrating a cloud account or folder to the shard (#153)

Question: what is a migration next to a #152 transfer, where does it land, what does the review step count, what is "verified" with the providers' own hashes, what does the summary export contain, and what may the source cleanup delete, after which confirmation?

Model. A migration is a transfer job of kind `migration` (migration 013 adds `kind` to `transfer_jobs`): a copy from one of the member's own connections (`conn:<id>`; shares and the home are refused with `VALIDATION`) into the member's home, never the other way (out of v1). `POST /api/v1/migrations` takes `{ from, path, dir, name }`: the cloud folder (`/` is the whole account) and a new folder `name` inside the home folder `dir`. The job has one item, the cloud folder, which lands in `dir/name` with "keep both", so a migration always creates its own folder and never mixes with or replaces what the member already has; a name already taken becomes `name (1)`. Everything else is #152: resumable after a restart, bounded workers, progress over the same SSE stream, the transfer panel. A failed item is not retried by itself; the member migrates that folder again.

Review. Before the start, the wizard asks `GET /api/v1/migrations/scan?source=&path=`, which walks the cloud folder and answers files, folders and bytes. The walk stops after 50,000 entries or 15 seconds and then says so (`complete: false`, the wizard shows "at least"), so a huge account does not hold a request open for minutes. The scan is information only; the job lists the folders itself as it goes.

Verification. Every file is checked by size and by SHA-256 against what landed in the home (#152). In addition, where the provider's listing gives a hash of the file, the bytes received are hashed with that algorithm too and compared: `read` may return `hash: { algorithm, value }`. Google Drive gives `md5Checksum` and is checked; Dropbox's `content_hash` and Graph's `quickXorHash` are their own block algorithms and are left for a later issue (*Known drift*). A mismatch is `VERIFY_FAILED`. Each item records what it was verified by (`size`, `sha256`, `md5`) for the summary.

Summary and export. The wizard's job page shows the verified count and bytes and every failed item with its reason (the panel already lists them). "Export summary" downloads `GET /api/v1/transfers/:id/report` as CSV, one row per item: status, cloud path, shard path, type, bytes, verified by, error code. It is streamed from the rows. Header and codes are fixed English machine names, not translated, so the file means the same thing whichever language the member uses. Every cell is quoted, and the only free text in it is paths, which start with `/`, so no cell can start a spreadsheet formula.

Cleanup. Only after a migration has ended (`JOB_RUNNING` otherwise), "Delete verified originals" asks `GET /api/v1/migrations/:id/cleanup`. It answers the number and bytes of verified files and a single-use confirmation token (16 random bytes; only its hash is stored, valid 10 minutes). The `<AppDialog>` shows those numbers and says the files go to the provider's trash. Only "Delete originals" in that dialog sends `POST /api/v1/migrations/:id/cleanup` with the token; a missing, wrong or expired token is `CONFIRMATION_REQUIRED` (428) and nothing happens. The cleanup is its own job (kind `cleanup`, its `origin` the migration), with one item per verified file of the migration, and nothing else: failed, cancelled and unlisted items are never part of it. Right before deleting, each item is checked again. The shard copy must still be a file of the verified size whose SHA-256 is the one received (`COPY_CHANGED` otherwise: it was changed, moved or deleted on the shard). The cloud file must still have its size and modified time from the migration (`SOURCE_CHANGED` otherwise: it changed in the cloud since). Only then is it deleted, into the provider's trash (#149–#151), never permanently. A cloud file already gone counts as done. Folders are never deleted: a folder is not something that was verified, and deleting one would take files added in the cloud since the migration with it. Empty folders therefore stay in the cloud. Deleting cloud files is the purpose the issue states, and each one lands in the provider's trash, so this needs no owner decision.

UI. "Move to shard" in the sidebar opens the wizard (`/migrate`): pick the connection and the folder (or the whole account), pick the home folder and the new folder's name, review the scan, start. The job page (`/migrate/<id>`, also linked from the transfer panel) shows the progress, then the summary with the export and the cleanup, then the cleanup job's result.

## 2026-10-15: versions of files (#154)

Question: which overwrites keep a version, where do versions live and how are they capped, what happens to them on move, delete and permanent delete, what may a share do with them, which providers can restore, and what does the drawer show?

When. A version is kept whenever the content of a file in the home is replaced in place: `PUT content` and tus with "replace" (an upload, also through a share with `edit`) and restoring a version. The replaced bytes are renamed into `<home>/.files/versions/<id>` (16 random bytes, hex) in the same transaction that puts the new bytes in place, with a `versions` row (migration 014: member, path, size, the content's modified time, creation time); nothing is copied. "Replace" in move, copy and trash restore keeps sending the item in the way to the trash, as before: the whole item (a folder too) is recoverable there, and the versions of a file replaced that way go to the trash with it. A new file and "keep both" keep nothing.

Caps. Per file, at most `FILES_VERSIONS_MAX_COUNT` versions (default 10) holding together at most `FILES_VERSIONS_MAX_BYTES` (default 1 GiB). After each new version the newest ones are kept while both caps hold; from the first that does not fit, every older one goes, bytes first and then the row. A single version larger than the byte cap is therefore not kept. The caps are configuration, not per member, until the storage overview gives the admin a page for such settings. Versions lie under the home, so they count towards the member's quota (an overwrite needs room for the new bytes while the old ones stay as a version).

Moves, trash, purge. `versions` is in `PATH_TABLES`, so a rename or move (also of a folder above) takes the rows along. A new `trashColumn` makes a delete to the trash hand the rows to the trash item (`trash_id`) instead of removing them; they are then not live, so a new file at the old path starts without them. `TRASH_TABLES` gets the table with a `pathColumn`: restoring the trash item brings the rows back at the path it lands on (also a "keep both" name), and `purge` removes their bytes before the trash item's and deletes the rows with the trash row. Rows a move finds at its free target (left by a change outside the app) are not removed, since they stand for bytes on disk.

Restore. `POST /api/v1/versions/restore` renames the version's bytes onto the file and keeps the content it replaces as a new version, in one transaction; the restored version leaves the list. A share with `edit` may restore (it may overwrite the file anyway), one with `read` may list and download. Downloads (`GET /api/v1/versions/content`) are always attachments. Version ids are checked against the member, the path and the live rows, so another file's or member's version is `NOT_FOUND`.

Cloud. `GET /api/v1/versions` lists the provider's revisions (the newest marked `current`, since it is the file itself). Dropbox restores with `files/restore`, OneDrive and SharePoint with `restoreVersion`; the provider keeps the replaced content as a revision itself. Google Drive's API has no restore: it would mean downloading the revision and uploading it again, which is left until someone needs it, so Drive lists revisions without a restore button (`NOT_SUPPORTED`, a new error code, 501). Cloud revisions are not downloadable in v1 (no route needs a provider-specific revision download yet).

UI. The details drawer of a file has a "Versions" section: newest first, date and size, "Download" (home) and "Restore" (with `edit`), each with an accessible label naming the date; a source without versions leaves the section out, a file without versions says that replacing it keeps the old content. A restore needs no confirmation, since nothing is lost: the replaced content becomes a version. After a restore the folder relists.

Not in this issue: a diff view (out, as the issue says), Drive restore, cloud revision downloads, versions for edits made outside the app.

## 2026-10-15: favourites across sources (#155, absorbs #28)

Question: what can be starred, how do favourites follow moves and deletes outside the home, what does "unavailable" mean and when is it decided, in which order are they listed, and what does a favourite open?

Model. A `favourites` row (migration 015) is `{member, source, path, type}`, one per item (`UNIQUE (user_id, source, path)`), for any source the member can read: `home`, their own `conn:<id>`, and `share:<id>` (the path inside the share). `POST /api/v1/favourites` resolves the source with `resolveSource` and `stat`s the item, so only something the caller can reach is starred and the stored path and type are the backend's; starring again answers the existing row (200). The root of a source is refused (`PATH_INVALID`): it is already in the sidebar. `DELETE /api/v1/favourites/:id` removes only the caller's own row; another member's id is `NOT_FOUND`. There is no limit on the number; it is a list a person curates by hand.

Moves and deletes. In the home the table is in `PATH_TABLES` with `sourceColumn`, so a rename or move (also of a folder above) rewrites the rows and a delete removes them, in the operation's transaction (#137). A delete removes rather than orphans: a favourite is a shortcut, and a shortcut to something in the trash helps nobody; restoring the item does not star it again. In another source the provider has no transaction, so the sources route rewrites (move) or removes (delete) the caller's rows of that source once the provider call has succeeded. Changes made elsewhere (at the provider, by the owner of a share, or by a transfer job between sources) are not followed; such a favourite opens its folder, which shows the truth.

Unavailable. Unlinking a connection marks its favourites gone (`gone_at`, a new `goneColumn` of `PathTable` that `orphanSourceRefs` sets instead of deleting) in the unlink's transaction. A gone row is never resolved again, even if the same account is connected again (that is a new connection id and a new source). In addition the list asks `sourceFor` for each source still in use, so a revoked or orphaned share also shows as unavailable. Availability is decided only by resolving the row's own source; a row is never matched against another source with the same path (#95). An unavailable favourite stays in the list with "Unavailable" and "Remove", and has no "Open", so the member sees what is gone instead of it silently disappearing.

Order. In the order they were starred (oldest first), so entries keep their place as the list grows.

Opening. As in search and Recent: a folder opens itself; a file opens its folder with `?select=`, which selects and focuses the file.

UI. The star is a toggle button (`aria-pressed`, labelled "Favourite: <name>") in every row of the list, the row menu has "Add to favourites" or "Remove from favourites", and the details drawer has the same toggle. All three act on the one item, never on the selection. Favourites sits in the sidebar before Recent (spec §3.8 order) with a line star icon; the view reuses the Recent table (name, location as source and folder, "Open", "Remove") and has its own empty-state sentence (#127).

Not in this issue: starring from the gallery view (it has no row menu yet), reordering, and following changes made outside the app.

## 2026-10-15: storage overview and per-member quotas (#156, absorbs #30 and #63)

Question: what counts as a member's usage, which operations are checked against the quota (and why a restore, which moves bytes already counted), where do the largest folders come from, what may the admin do, how are quotas entered, and what does a member see without a quota?

Usage. Everything under the member's home counts, as the upload check (#140) already measured it: the files, the trash, kept versions, and staging (tus uploads in progress, interrupted copies). The overview shows these four parts and their sum, measured on disk the same way the check measures, so the figure the member sees is the one the check uses. Thumbnails live outside the homes and do not count.

Checks. Every operation that adds bytes to a home is refused with `QUOTA_EXCEEDED` (507) before anything is written: tus creation and `PUT content` (as before, and again while they stream), a copy within the home (the size of the source's tree), a trash restore (the item's recorded size), and transfer and migration items into the home (the home's `write`, which gets the announced size, so an item fails before its body is read). A restore moves bytes that already count, but the trash frees them by itself after the retention time; a restore keeps them for good, so it needs room like new bytes would. Without this, a member at the quota could grow their live files by trashing and restoring. A move within the home and a version restore swap bytes already counted and are not checked. A quota lowered below the usage removes nothing; it only refuses what comes next. Copies and restores measure before they run and do not reserve (only tus uploads reserve, #140); two started at the same moment can together pass the quota by one of them, which is noted under *Known drift* rather than locked, since the quota is a family-scale limit and not a billing boundary.

Largest folders. The ten largest folders of the home, anywhere in the tree (a parent appears above its biggest child), summed from the file rows of the name index (#145). The index is kept current by every write in the app, so this is the "computed incrementally" option of the issue and never walks the disk; changes made outside the app show after the rebuild command, like search. The trash is not in the index and is shown as its own part of the usage instead.

Provider quota. `GET /api/v1/storage` asks every connection's `quota()` at once (Drive's `storageQuota`, Dropbox's space usage, Graph's drive quota; #149–#151). A provider without a limit has no `total` and is shown as "used · no limit" without a bar; a connection that fails (signed out, provider down) is shown with its error code, and the rest of the page still answers, as in search. No other member's connections are ever asked.

Admin. The admin is the role from the OIDC claim (`FILES_OIDC_ROLE_CLAIM`/`FILES_OIDC_ADMIN_VALUE`), mapped at every sign-in; there is no other way to become admin, and without the claim configuration nobody is. Only the admin reads `GET /api/v1/admin/members` (everyone who has signed in to Files once, the admin included, with usage and quota) and sets `PUT /api/v1/admin/members/:id/quota` (`{ quotaBytes: n | null }`, a whole number of bytes ≥ 0, `null` removes it); everyone else gets `FORBIDDEN` (403), also for their own row. The admin may set their own quota. An unknown member id is `NOT_FOUND`. The members page is in the sidebar only for the admin; a member who opens `/members` sees the server's refusal.

Entry. A number plus a unit, MB or GB, in powers of 1000 like every size the app shows (`format.ts`), so "50 MB" entered is "50 MB" displayed. Decimals with a point or a comma are accepted; anything else, or a negative number, is marked invalid in the form and not sent. No confirmation: setting or removing a quota loses nothing.

Without a quota. The overview shows "used · no quota" and the breakdown, but no bar, because a bar needs a limit. With a quota the bar turns red from 90 %.

Not in this issue: per-member version caps (they stay configuration, #154), a shard-wide default quota for new members, notifications when a member nears the quota, and the share or upload target's quota for uploads into another member's share (#152).

## 2026-10-15: WebDAV and app passwords (#157, absorbs #21, #105, #122)

Question: where does WebDAV live and how does it authenticate, what is an app password and how is it found without trying every hash, which parts of class 1 and 2 are served and how, where do locks and dead properties live, what does DELETE do, and does the intermediate-directory window between resolving a path and using it (#134) need closing now that a second protocol exists?

Address. WebDAV is `/dav/` on the app's origin (`server/src/dav/`), the member's own home and nothing else: no shares, no cloud sources (out of scope), so a client sees exactly "My storage". It is not under `/api/v1/`, because it is a protocol of its own, not an API route: clients mount the URL itself, and `routeInventory.test.ts` had reserved `/dav/*` for it. The routes are `/dav` and `/dav/*` for OPTIONS, GET, HEAD, PUT, DELETE, PROPFIND, PROPPATCH, MKCOL, COPY, MOVE, LOCK and UNLOCK, registered in their own encapsulated scope whose only body parser hands every body on as a stream, so a PUT of a JSON file is never parsed or buffered.

Authentication. The routes carry `config: { appPassword: true }`, the one auth mode besides the session: the guard takes HTTP Basic, ignores the session cookie entirely there, and answers 401 with `WWW-Authenticate: Basic realm="FreeShard Files"`. Ignoring the cookie means a web page can never reach WebDAV with the member's session, so WebDAV needs no CSRF token; a request that carries an `Origin` other than the app's own (a page sent it) is 403 as well, since a browser may remember Basic credentials. The other way round, an app password opens no other route: everything else still decides on the session alone. The user name is not checked: the app password names its member, so any user name works and the settings page says so; asking for an exact one would only add a way to type it wrong.

App passwords. 40 characters from `a–z` and `2–9` without `l` and `o` (5 bits each, 200 bits), generated on the server and shown once in the create answer (`Cache-Control: no-store`). The first 8 characters are the lookup prefix, stored in a unique column; the row holds the argon2id hash (`@node-rs/argon2`, as for public links) of the whole password. A sign-in reads the one row with its prefix and verifies that hash; no other row is ever touched, which the test proves with rows whose hashes no verifier accepts. Clients send the password with every request and argon2id is slow by design, so a verified password is remembered in memory for five minutes, keyed by its SHA-256 and bound to the row id; the row is still read on every request, so a revoked password answers 401 on the very next one. A member may hold 20 (`APP_PASSWORD_LIMIT`, 409, "revoke one first"): one per device is the expected use, and a bound keeps the table and the settings list small. Labels are 1–100 characters. `last_used_at` is written when a password is verified (at most every five minutes per client). Revoking deletes the row after a confirmation (`ConfirmDialog`), since it cuts a device off. Settings (`/settings`, new in the sidebar) shows the address, the hint about the user name, the form, and the list with created and last-used dates; a new password opens an `<AppDialog>` with the password selected and "Copy"; a refused create (the limit) is shown in the page's alert line and keeps the label in the form (#122).

Protocol. Paths are decoded from the request path segment by segment, never through `new URL`, which would quietly resolve `..` and `%2e%2e` into another path instead of refusing it; a decoded segment holding `/`, a raw `#` in the request (litmus: a DELETE of `coll/#frag` must not delete `coll`), and everything `normalizeUserPath`/`resolveInRoot` refuse (`..`, symlinks, `.files/`) answer 400. Destination and `If` tags are parsed the same way; their scheme and host are not compared (behind the shard proxy the client's host is not ours to know), a path outside `/dav/` is 502. Hrefs percent-encode every segment (`encodeURIComponent`), collections end in `/`. The ETag is the size and modification time (`"<size>-<mtime ms>"`, hex), the same in PROPFIND, GET, HEAD and `If`. PROPFIND serves Depth 0 and 1 and refuses infinity with `propfind-finite-depth` (403), as RFC 4918 allows: a whole home in one answer is a denial of service. Live properties: creationdate (the modification time; the disk keeps no creation time), displayname, getcontentlength, getcontenttype, getetag, getlastmodified, resourcetype, supportedlock, lockdiscovery, and the RFC 4331 quota properties on folders when asked for by name (they walk the home, so not in allprop). XML bodies are read up to 1 MiB and parsed with `@xmldom/xmldom`; a DOCTYPE is refused outright, so no entity is ever declared or expanded. GET always answers as an attachment with `CSP: sandbox` and `nosniff`, like the API, because a browser that has the credentials must never run a stored HTML file on the app's origin; a GET of a folder is 405.

Writes go through the home's `LocalBackend`, so every rule of the home holds: PUT streams with `replace` (an overwrite keeps a version, #154) under the upload size limit and the quota (507, #156); MKCOL and PUT need an existing parent (409), because the backend would create missing folders; COPY and MOVE honour `Overwrite` (default T): an existing target goes to the trash through the backend's "replace" (204), `F` is 412; a COPY with Depth 0 of a folder makes an empty folder. DELETE is the backend's `delete`, the one move to the trash (#138), so a WebDAV delete is restorable like any other (#105; the test turns red if the trash step is removed). Deleting the root is 403.

Dead properties. PROPPATCH stores each property element as XML in `dav_props` (migration 016), one row per item and property. The table is in `PATH_TABLES`, so properties follow a MOVE and go with a DELETE in the backend's transaction; a COPY copies them (deep or depth 0) right after the copy. A request that tries to set or remove a `DAV:` property fails as a whole: those are 403, the rest 424, and nothing is stored (RFC 4918 §9.2). Restoring an item from the trash does not bring its properties back, as with shares.

Locks. Exclusive and shared write locks, Depth 0 or infinity, in memory per member (`dav/locks.ts`): the app is one process, a member's home is reachable only by that member, so a lock only coordinates the member's own clients, and a restart only means a client locks again. Timeout is the client's, capped at a day (one hour if none). A lock on an unmapped URL creates an empty file (201). A change needs the token of a lock that protects the item (the item's own locks, a depth-infinity lock above it, and for a new or removed item the locks of its folder); a deep change (DELETE or MOVE of a folder) also needs the tokens of locks beneath it; otherwise 423 with `lock-token-submitted`. A token counts as submitted when it appears anywhere in `If`. The `If` header is evaluated first: tagged and untagged lists, `Not`, state tokens (true when that lock protects the resource) and ETags; if no list holds, 412. A LOCK without a body refreshes the lock named in `If`, also through a member of a locked folder. UNLOCK needs a token whose lock protects the request URL (409 otherwise). DELETE and MOVE end the locks of what they took away.

Intermediate directories (#134 revisited). `resolveInRoot` checks every component for symlinks, then the operation uses the path, so a component swapped for a symlink in between would be followed. A second protocol does not change who can make that swap: neither the API nor WebDAV can create a symlink (WebDAV has no BIND or link method here, and unknown methods do not match a route), renames stay inside the home, and hard links are made only for files the app itself placed. Only someone with a shell on the host could plant one, and such a person can read the data directory anyway. The window therefore stays as it is, and no `openat2`-style resolution (which Node does not offer) is added; the tests plant symlinks on disk, as a host could, and check that WebDAV refuses them as a file, as an intermediate folder, as a COPY source and as a MOVE target.

Verification. litmus (Debian trixie's package, `server/test/litmus/Containerfile`) runs in a container against the real server through `pnpm test:litmus` (vitest with its own config, skipped without podman or docker, never counted as passed): basic 16/16, copymove 13/13, props 30/30, locks 41/41, no warnings. The rclone round trip (`server/test/davRoundTrip.test.ts`) runs where rclone is installed; a scripted client with plain WebDAV requests does the same round trip everywhere.

Not in this issue: WebDAV for shares and cloud sources (out of scope), the outgoing WebDAV client (#131), rate limiting of wrong app passwords (the 160-bit secret part makes guessing hopeless, and a wrong prefix costs one indexed lookup, no hash), and persisting locks across restarts.

## 2026-10-15: Installable PWA and Web Share Target (#158, absorbs #47)

Question: what the service worker caches, how a share from the phone reaches the upload flow when the share sheet's POST carries no CSRF token, where the shared files wait while the member picks a folder, what the server does with a share it receives itself, and which folders a share may go to.

Shell only. The service worker (`web/public/sw.js`, plain JavaScript copied into the build, scope `/`) caches index.html and what it references (the hashed bundle, manifest, icons) at install, and later hashed assets on first use. App pages are answered network first, so a new build shows at once, and from the cached shell without network; when index.html changes, assets of the older build are dropped, so the cache holds one build. `/api`, `/auth` and `/dav` are never answered from the cache: no file data is offline in v1 (spec §2.1), and the shell shows an offline banner plus the "No connection" alert instead of stale listings. Only the built app registers the worker; under the dev server a cached shell would hide every edit.

The share. The manifest's `share_target` posts `multipart/form-data` (field `files`, any type) to `/api/v1/share-target`. The service worker takes that POST in the browser: the files go into an IndexedDB inbox (`files-share-inbox`) under a random id, and the browser is redirected to `/share-target/<id>`. There the member sees the files, picks a folder with the `FolderPicker`, and "Save here" hands them to the uploads store (#140) like a picked file: tus into the home with the session's CSRF token, the collision dialog, the upload panel. Once the batch settles the folder opens; the inbox entry is deleted when nothing failed (a failed item can be retried from the panel), on "Discard", and after a day otherwise. A member without a session lands on the page, is sent to login by the API's 401, and comes back to the same page with the files still in the browser. The CSRF rule stays whole this way: the share sheet's POST never changes anything on the server, and the upload is an ordinary authenticated request.

The server's route. `POST /api/v1/share-target` is reached only when no service worker took the share (Files never opened on the device, or a browser without one). It cannot accept the files: the POST has no CSRF token, so any site could plant files in the member's account through it. It is therefore `config: { public: true }` (stated in `routeInventory.test.ts`), accepts the multipart body without reading it (Node discards it after the answer), and answers 303: without a session to `/auth/login?returnTo=/share-target`, with one to `/share-target`, which says the share did not arrive and to open Files once and share again. Nothing of the body is parsed, buffered or stored; the test checks the data dir for the shared bytes.

Target. My storage only, any folder in it. Cloud connections and shares with `edit` would need a source picker and their own upload paths (a direct PUT per file for clouds); YAGNI for "photos from the gallery into a folder". Manifest name "Files", the product name, as in the page title; the manifest has one language, and the UI's own title stays localised.

Not in this issue: offline data, sharing text or links (only files are accepted), saving into cloud sources or shares, and an install prompt inside the app (the browser offers installation itself).

## 2026-10-15: quota reservations for direct writes and copies (#197)

Question: parallel `PUT content`, WebDAV `PUT` and copies each compared their own bytes against the whole free space, so together they exceeded the quota. How do they share it, and what does a write without a declared length get?

Decision: they reserve before reading a byte, like tus creation. A reservation is held in memory per member (the app is one process) and is taken and released under the member's lock that restore and purge already use; tus creation now walks and inserts under that lock too. The free space is the quota minus the disk walk minus open tus uploads minus the reservations in flight; the walk leaves out the staged path of each write in flight, so its bytes count once, through the reservation. A write with a declared length reserves that length; one without reserves all the free space left and may fill it, so other writes are refused until it finishes. A copy reserves the source's size and is refused if the staged copy came out larger.

Why: the issue asks for exactly this, and a chunked request without length is rare (browsers, rclone and the WebDAV clients send one); growing a reservation per chunk would need the walk and the release to agree on every chunk, which is more machinery than the case is worth (YAGNI). A database table would survive a restart, but a restart ends every write in flight anyway.

## 2026-10-15: Drive thumbnails of Google Docs, and where the token goes (#203)

Question: Drive gives Google Docs, Sheets and Slides a `thumbnailLink` on `docs.google.com/feeds/vt?…&sz=s220`, not on `lh3.googleusercontent.com/…=s220`, and the backend answered 500 for it. It also sent the bearer token to the thumbnail host, against the rule that content hosts never get the token. Which hosts get the token, and how is the size set?

Decision: a `thumbnailLink` is taken only from Google's thumbnail hosts (`docs.google.com` or `*.googleusercontent.com`, https; `DriveEndpoints.thumbnailHost`), and anything else is still an error. That first request carries the bearer token. A redirect from it is followed like a download: only to a content host and without the token. The size is set in either shape: `=s<n>` at the end of the path, or `sz=s<n>` in the query. A link in neither shape is fetched as it is, and the result is resized by sharp anyway. A 404 from the link is no thumbnail (`NO_THUMBNAIL`).

Why: Drive's file reference says the `thumbnailLink` of a file that is not shared publicly must be fetched with a credentialed request, so leaving the token off would break thumbnails of private files. Limiting the token to Google's own thumbnail hosts and to the first hop keeps it away from every pre-signed URL. The fake now serves both shapes, needs the token on both links and records any token that arrives on the pre-signed hop, so a regression shows in the suite.

## 2026-10-15: optional provider fields: Graph drive quota, Dropbox search paths (#205)

## 2026-10-16: sharing on every source, upload into edit shares, renamed cloud items (#208)

Question: the issue asks for shares and links of Google Drive and Dropbox items driven through the UI, for a member who uploads into an edit share, previews a shared file, and a visitor who previews an image inside a linked folder. The SPA offered "Share" only in the home, no upload in any share (#146, #149), only "Download" for a shared file, and only downloads in a linked folder. What changes, and what happens to a share or link when its cloud item is renamed or moved?

Decision. "Share" (row menu and details drawer, with the public links in the same dialog) is offered in the member's own home and own cloud connections, never in a share, since a share is never shared on. Upload (button and desktop drop) is offered wherever the caller may change things: the home, their own connections and shares with `edit`. Into a connection or a share it is one streaming `PUT content` per file, as for connections since #149; tus stays home-only. The bytes land in the owner's source through the share, so in a home share they count against the owner's quota and keep the owner's versions, and in a cloud share against the owner's provider account; `FILES_MAX_UPLOAD_BYTES` applies as for every `PUT`. "Shared with me" offers "Preview" next to "Download" for a shared file and opens the preview overlay on the share's `/`. A visitor of a folder link gets "Open preview" (new tab, `?inline`) for each file whose type the server shows inline, as on a file link; it counts as a download. A share or link of a cloud item names the owner's path, like one of the home, but only the home's moves cascade (`PATH_TABLES`). A cloud item renamed or moved at the provider, or by the owner through their connection in the app, leaves the share and the link at the old path: they answer `NOT_FOUND` (404). On Drive this shows after at most the 30 s path cache. The owner shares the item again. An unlinked connection still orphans them (410, #148).

Why: spec §2.1 says shares and links work on every source. The server has supported `conn:` sources since #148, so the UI was the missing part. The quota question #146 left open has a plain answer: a share writes into the owner's storage, which the owner opened by granting `edit`. A cloud share has no shard quota at all. Following cloud renames would need the provider's item id in the share row (a migration plus an id lookup per provider). An item placed at the old path later is what the share then shows. That is acceptable while the owner controls their own account, and tracking by id is left until someone needs it (YAGNI). `server/test/sharingMatrix.test.ts` pins the server side for home, Drive and Dropbox; `e2e/cloud-sharing.spec.ts` covers the UI.

## 2026-10-16: Microsoft's real content hosts (#202)

Question: personal OneDrive sends downloads from `my.microsoftpersonalcontent.com`, and SharePoint and OneDrive for Business thumbnails redirect to `<region>-mediap.svc.ms/transform/thumbnail`. Neither was on the content-host allowlist, so those downloads, copies to the shard and every such thumbnail failed with 500. How far does the allowlist widen?

## 2026-10-16: Drive uploads: the Range of a 308, and empty files (#204)

Question: Drive's 308 names the bytes it kept, which can be fewer than were sent. How does the backend resend, and how does a 0-byte file go up when `bytes */0` is Drive's status query?

Decision: every session `PUT` starts at the last byte Drive confirmed. The bytes it did not keep move to the front of the next chunk, so chunks keep their 256 KiB multiple and at most two chunk buffers are held. A 308 without progress, with an unreadable `Range`, or confirming more than was sent fails the upload and cancels the session. It never loops. An empty file goes up as one `uploadType=multipart` request, which is `POST` for a new file and `PATCH` for a new revision, and no session is opened for it. The fake Drive now persists only part of a chunk when a test asks (`persistOnly`), never completes a session on a status query, and accepts multipart uploads.

Why: Drive's resumable-upload guide says to resend from the reported Range. A multipart upload is a documented way to create a file with metadata and any content, including none, and it avoids the open question of whether a status query completes a session. Failing on a stuck session is better than resending without end, and the member can retry the upload.
